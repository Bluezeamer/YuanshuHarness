# 子代理与后台任务

Author: bluezeamer
Status: 现行
Date: 2026-11-03
Verified: 2026-11-19（对着代码核对：`subagent/{limits,tools,collab}.ts`、`job/{tools,manager}.ts`、`api/{jobs,flows}.ts`、`store/{defaults,jobs}.ts`、`provider/limiter.ts`、`session/{delegation,capabilities}.ts`、`permission/extension.ts` 的相关段，以及 web 端 `features/chat/status/` 的子代理树与后台任务块；`subagent/runtime.ts`、`fork.ts` 只核对了符号是否存在）

定义子代理怎么派发、交付、停止，以及统一的「后台任务」机制。能力与权限的求值见 [`prompt.md`](prompt.md)，提示词与状态如何送达见 [`prompt-delivery.md`](prompt-delivery.md)，团队见 [`team.md`](team.md)，动态工作流见 [`workflow.md`](workflow.md)，术语「目录」「工作区」见 [`workspace.md`](workspace.md)。
底座：子代理是独立会话加父子记录（`subagents` 表）；发起、等待、返回、权限、上下文与上限各条见下。

## 1. 原则

- **S1 默认阻塞**：直接调用任何工具都是阻塞的，结果就是工具结果。
- **S2 后台是包在工具调用外的一层，不是新工具**：`job_start` 把任意一次工具调用放到后台，完成时回调。**没有 wait 工具**：不轮询、不睡眠，要么做别的，要么结束本轮，回调会唤醒。要汇合几个并行任务，在同一条消息里并发发起几个阻塞调用。
- **S3 提醒不终止任务**：到提醒时间只是把控制权还给调用方，由它决定继续等、查看、追问还是停止。
- **S4 失败立即向直接调用方反馈**，只报给直接调用方，链式靠逐层传递。
- **S5 停止是链式的**：停掉一个任务，它名下的一切（后台命令、子代理、子代理的任务）全部停，不留僵尸；调用方异常退出同样如此。**唯一例外：用户停止根 agent（与用户对话的那个）不停它派发的任务。**
- **S7 通信只有两条通道**：父 → 子 `message_subagent`，子 → 父 `deliver`。子代理不向父推送运行中的消息（不打扰调用方，与审批同一原则），子代理之间不通信；父想了解进展靠拉取：`job_list` 带 id 看最近动作，或读协作区里的文件。运行中的推送与成员间通信只属于 agent teams（[`team.md`](team.md)）。
- **S6 框架工具**：`deliver`、`job_*` 等是运行时必需件，不受模式约束、不可取消勾选，见 `prompt.md` E6。

## 2. 工具面

| 工具 | 谁有 | 作用 |
|---|---|---|
| `spawn_subagent` | 能力单元「子代理」开 | 派发。参数：`task`；`agent`（缺省同调用方，fork 时不可指定）；`context`：`fresh`（默认）或 `fork`；`mode`（仅调用方没有激活模式时可选）；`model`（仅 fresh）；`directory`（`<host>:<name>`，缺省调用方当前目录；子代理只在这一个目录里工作、不能切换，见 `workspace.md` §3）；`tier`（只能更严）；`remind_after`。没有 `inherit_capabilities`、`inherit_history` 这类继承参数：上下文只有 fresh / fork 两种 |
| `message_subagent` | 同上 | `{id, text}`：对运行中或已交付的子代理继续说话。运行中排在当前步骤之后（steer），已结束则开新一轮（任务重新打开）。子代理缺信息时由父用它补充，不另设 `ask_parent` |
| `deliver` | 仅子代理会话 | 交付，见 §5 |
| `job_start` | 全部会话 | `{name, arguments, label?, remind_after?}`：后台运行任意一次工具调用（含声明外的工具、慢的 MCP 工具），立即返回任务 id。形状同 `call_tool`，内层走同一套校验、钩子与权限（经 `ctx.executeTool`）；观察期（0.3 秒）内就结束的（被拦、参数错、一闪而过）结果直接作为 `job_start` 的返回，不产生回调 |
| `job_list` | 全部 | 列出自己名下的任务；带 `id` 看日志。压缩后调用方不记得 id，靠它找回 |
| `job_stop` | 全部 | 停止并链式停止；返回里列出一并停掉的任务 |
| `job_remind` | 全部 | `{id, every}`：设置新的提醒间隔并刷新计时 |

`bash`、`spawn_subagent` 等原有工具的参数不加 `background`，声明不变。持久进程就是一直不结束的后台任务；`bash` 没有 `timeout`（到点杀掉），换成提醒（`remind_after`）；没有 `port` 参数与「是否在监听」的探测，需要时写进 `label`。**子代理就是任务**：`spawn_subagent` 登记一个 `kind=subagent` 的任务，**任务 id 就是子代理 id**（`jobs.ref` = 子会话 id），`job_list / job_stop / job_remind`、回调、提醒、链式停止都走 `job/` 那一套，没有第二套机制；`job_start` 包着 `spawn_subagent` 时沿用外层那个任务。

## 3. 直接调用、后台任务与回调

| 事件 | 直接调用（阻塞） | 后台任务 |
|---|---|---|
| 完成 | 结果作为工具结果 | 回调消息 |
| 到提醒时间 | 这次调用返回「仍在运行，任务 #n」，任务继续跑，此后按后台任务处理 | 回调消息 |
| 异常退出 | 工具错误 | 立即回调 |
| 用户在子代理标签里停止它 | 工具错误「被用户停止」 | 回调 |

- **回调**是发给**直接调用方**的一条英文消息（框架口吻，与子代理自己写的话分开，见 §9）。调用方在跑：走 pi 原生的 steer，在下一步模型调用之前注入；空闲：唤醒它；调用方不在线的留着，下次发消息前补上。用户停止根 agent 时 `dropQueued` 会把这类系统通知保留下来（steer 与 follow-up 两个队列分别处理）。**不设合并窗口**，几个任务差不多同时完成时，pi 本来就会把启动过程中收到的消息并入同一轮。
- **提醒是周期性的**：每隔同样时间一次。缺省值取全局设置（设置 · 默认值里的「后台任务提醒」），**默认 10 分钟**（命令、其他工具、子代理统一一个数，可按自己的情况覆盖），调用时用 `remind_after` 覆盖，`job_remind` 可改；下限 10 秒。**`remind_after` 为 `0` = 不提醒，只对 `bash` 生效**（用于 dev server 这类常驻进程；对 `bash` 的阻塞调用，`0` 还表示不转后台、一直等）；其他工具与子代理必须有提醒，兜底防僵尸调用，让 agent 始终知道发生了什么，传 `0` 按参数校验报错。内容：已运行多久、最近一次输出距今多久、输出末尾（子代理给最近的动作），以及可选动作。
- **阻塞的 `bash` 到提醒时间转后台**：到点这次调用先返回「仍在运行，任务 #n」，命令改用自己的中止信号继续跑，此后外层调用被中止也不影响它。阻塞派发的子代理同理：到 `remind_after` 先返回并让子代理继续在后台跑，交付时回调；阻塞期间调用被中止，同样返回并保留子代理在后台。
- **日志**：后台命令的完整输出写 `<数据目录>/jobs/<id>.log`，回调只带末尾几行与路径。所有命令都在 Server 进程里跑（`bash` 与 `job_start` 同一套）。
- **自己发起的停止不再回调给自己**；别人（用户、上游的链式停止）停掉的，回调给直接调用方，否则它会一直等。子代理自己被停时，它名下的任务按「自己停」处理，不回调给它。
- **服务重启**：运行中的任务与子代理一律记为 `interrupted`、命令随之结束（dev server 不跨重启存活），下次发消息前由状态通知告知调用方；正常关闭时 `shutdown()` 先杀掉再记中断。
- 防轮询靠文案，写进 `spawn_subagent` 与 `job_start` 的描述和「子代理与模式」内置段：结果会自动送达；做不重叠的事，或简短告诉用户已派发后结束本轮。

## 4. 派发与上下文

- **fresh（默认）**：子代理从空白上下文开始，系统提示词与工具声明和根会话（同一 Agent 定义）逐字节相同，开头一直到开场消息之前都能共享缓存。Agent 与模型都与父相同时，直接沿用父的冻结物（`seedHead`）；父的声明里本不该给子代理的工具（`ask_user` 等）仍在，靠状态通知告知不可用，`deliver` 与 `job_*` 同样走通知。指定了不同的 Agent 或模型就不沿用，按自己的重新冻结。
- **fork**：沿用调用方的 Agent、模型、能力与工具声明（不能再指定）。**分叉点 = 发出这次 `spawn_subagent` 的那条 assistant 消息的上一条**（`fork.ts`，认 `call_x/n` 形式的内层调用 id），从父会话文件截出新会话文件（`pool.forkFile`），整条消息不进子代理的上下文，所以历史里没有 spawn 调用，也不需要补占位；当前轮前面已读的内容全部保留。并行派多个时从同一点分出，前缀相同，兄弟之间共享缓存。代价：模型在 spawn 之前写的话子代理看不到，意图要靠 `task` 写清楚（工具描述里写明）。
- **开场说明走第一条 user 消息**（fork 时接在分叉点后面），不进系统提示词，两种模式同一条路。内容（英文）：你是被派发的子代理；fork 时「前面的对话是继承的只读参考，不是要接着聊的线程」；任务；操作被拒说明超出能力边界，不要重试；`deliver` 的签名与用法；深度与模式规则。
- **不处理带签名的 thinking 块**：保兼容与前缀。
- **缓存不变式（有测试）**：同一 Agent 定义的 fresh 子代理与根会话，开头系统消息加工具声明字节相等。

## 5. 交付

- **`deliver({summary, report?})`**：只给子代理，用户不可见、不可取消。`summary` 是短结论，进父的上下文，schema 里限长（2000 字符），超了按普通参数校验报错；`report` 可空，长报告，由运行时存成协作区里的文件（`<数据目录>/collab/<根会话 id>/<子代理 id>/report.md`，只读子代理也能用，不需要写工具），父拿到路径和字节数，读不读、怎么读由父决定。子代理自己写进子目录的其他文件，自动列出。
- **声明方式**：走占位通道尾部注入（fresh 与 fork 一律如此），不进工具声明，所以不改前缀；开场消息里写明签名。
- **完成 = 调用了 `deliver`**。子停下、非异常、没交付、名下没有运行中的任务，就注入一条英文 user 消息：所有后台任务都已返回，工作做完就必须交付。名下还有任务在跑说明它在等回调，不提醒；**`remind_after: 0` 的常驻命令不算在跑的任务**，否则名下有 dev server 的子代理永远不会被催交付，子代理的完成检查与会话状态都忽略它。连续提醒 3 次仍不交付，就把最后一条回复当结果、标注「未显式交付」并结束。
- **交付时名下还有运行中的任务**：拒绝并列出，要求先等或先停。
- **`deliver` 是缓存区，可多次调用，后一次覆盖前一次，以最后一次为准，这一轮结束时才送出**；父收到的是最后一次。已交付的子代理被 `message_subagent` 唤醒后，要么重新 `deliver`，要么只回复 `work done` 表示对交付没有影响（父收到「交付没变」的回调）。
- 父收到的是框架口吻的一条：子代理 id、状态、`summary`、`report` 路径，与子代理自己的话分开。

## 6. 限额

- 深度 3、每个调用方同时直接运行的子代理 10、整棵树同时运行 50；全局生效，在设置 · 默认值里调（`SubagentLimits`），每次派发即时读。
- **「同时运行」指存活的**：没交付也没被停止的子代理。阻塞调用的子代理一交付就释放名额，按顺序阻塞地创建再多也不会撞上限。
- **模型并发是另一种资源**：供应商设置里的「最大并发请求数」（`providers.max_concurrent`，缺省 50，1–1000），本地部署的模型按其上限填（如 2）；超了在服务端**排队**（`provider/limiter.ts`，按供应商先来先放行），不拒绝。限流包在会话的 `agent.streamFunction` 上（会话工厂与审核会话都用 `limitRequests`），流结束 / 出错 / 被中止时释放，排队时被中止就放弃；上限每次现取，设置里改了之后的放行就按新的来。父阻塞在工具调用里并不占请求，所以排队不会死锁。
- **工作流的 agent 不计入这两个存活数**（见 [`workflow.md`](workflow.md) §5）：它们走工作流自己的并发上限；它们名下再派的子代理照常计入。
- **不设累计派发上限**：只有「最大存活 50」与「最大并发请求 50」两个数，二者不是一回事。
- 存活数超限**直接返回错误并写明「别重试」**，不排队：阻塞的子代理若排队等名额，名额被在跑的占着、其中包括正在等它的父，会死循环。唤醒已交付的子代理同样检查。
- 深度已满的子代理没有可用的派发工具：靠 `tool_call` 钩子确定性拦截，再在开场说明里写明；不改声明。

## 7. 权限与模式

- **子代理没有审批通道**，要审批的操作直接拒绝，不冒泡给用户（审批要在有上下文的地方发生）。**不把被拒的操作转述给父**：子代理看到工具调用失败，自己判断是调用有误还是能力边界，换办法，或在交付里如实说明做不到什么；不为此打扰调用方。
- 档位：继承调用方的权限覆盖（派发上限与会话生效档取较严的一档，两处判定合成 `pool.effectiveTier`），最高到「模型」档，永远到不了「通过」档，派发时可只收得更严。
- **子代理的工具由它自己的 Agent 定义决定**，不要求是调用方的子集，这样才做得出「协调者只读、干活者能写」。防越权靠权限收窄与模式继承。
- **模式**：调用方有激活模式，子代理继承，`mode` 参数不开放；没有则可从会话的可用模式清单里指定一个。子代理的可用清单只有这一个，且没有 `switch_mode`，切不出去。
- **`switch_mode`**：框架工具，agent 能看到可用模式并自行切换；**默认切换要人批**（设置 · 工具与能力页里可改成放行；决定：模式可以「增加」基线里没有的工具，模型自己切进去就等于自己加了工具，所以不能默认放行）：切进模式、退出模式都弹审批（`list` 只是查看，不弹；权限扩展里的 `switchModeGate`）；通过档与「放行」不弹，自动审核档也不送审（给自己加工具不由审核模型代批）。
- **可派发清单**：会话级设定，用户勾选，默认配置里带一份，与可用模式清单同一类；`spawn_subagent` 仅在清单非空时声明。Agent 的 `description` 约定写成「何时该用我」。作为我们生成的内置段（英文，用户不可改）：初始清单进冻结物，之后的变化走状态通知。（未实现，见 §10。）
- **「子代理与模式」内置段**（`session/delegation.ts`，标签 `<delegation>`）：我们生成的英文说明，在 `pool.liveRender` 里追加，所以进冻结物，之后 Agent 清单或模式清单变了走状态通知的「段已变化」。只在会话有相关工具时生成，写明：模式能切、切换要审批、派子代理时模式怎么继承、fresh 与 fork 的区别、子代理不能切模式、反轮询，并列出可派发的 Agent 定义的名称与描述；团队与工作流各有一两句何时该用。
- **子代理能力是一个整体单元**（`unit:subagent`，`CAPABILITY_UNITS` 把它展开成 `spawn_subagent` + `message_subagent`），开关只有一个，不细分到单个工具（工具之间相互依赖才能正确调用）；Studio 能力页把这两个工具合成一项「子代理」放在「能力单元」组。

## 8. 协作区

- **位置**：每个根会话一个隐藏的虚拟主机 `collab`（与附件区同一类，`CollabArea.env` 是一个 `VirtualEnv`，不登记进 `directories` 表）：磁盘上是 `<数据目录>/collab/<根会话 id>/<子代理 id>/`（内部按子会话 id 分子目录），不在项目目录里、不进 git，但**模型看不到真实路径**，按 `host="collab"` 加 `/` 开头的路径寻址（`/<子代理 id>/report.md`、`/board.md`）。`pool.visibleDirectories` 给同一棵树的会话追加一个内存里的 `collab` 目录（树目录存在、或自己是子会话才出现）。**任何目录上的会话都能用**，包括 SSH 目录上的子代理、主目录在 ssh 上的根会话；控制流走事件，不靠文件。`CollabArea.virtualPath(rootId, abs)` 把 Server 的真实路径换算成虚拟主机里的路径，`ensureOwn` 在子代理启动时把它自己的子目录建出来。文字里的地址一律是 `host="collab", path="/…"`：子代理开场说明（所有子代理都给，不再看起始目录在哪）、交付结果里的 `Full report`、团队公告板与成员开场消息、工作流的大结果 `result.json`。`bash` 不经协作区（命令在目录所在主机上跑）。
- **权限**（`permission/extension.ts` 的 `judgeTarget` 与 `gate` 的写护栏，都在 `full` 放行之前、不看档位、不弹审批）：同一棵树的会话都可读，子代理只写自己的子目录，根会话不写（团队成员全部停止时 lead 可改公告板已有内容）；读写按真实位置判（符号链接指到树外按外部拒绝）；`transfer_files` 的两端同样按它判。它是内置放行路径、不弹审批，因为它在项目目录之外，否则「规则」「模型」档会按「目录外」处理。
- **生命周期**：随根会话删除（整棵一起清掉；子代理自己被删时留着），不做定时清理。`deliver` 的报告落在自己的子目录。
- **入口**：界面上没有协作区的浏览入口，见 §10。

## 9. 界面

右侧状态里的「子代理」块是一棵树（主代理 → 子代理，最多 3 层）：结束满 10 分钟折起来（`FOLD_MIN`）、「现状 / 全部」切换、没看过的失败不折；`/flows` 的执行体带 `ended`（落终态的时间）和来源 `source`（`task` 模型自己派发的 / `team` 团队成员 / `workflow` 工作流里的 agent，另带 `member`、`run`）。**子代理树只收 `task`**：团队成员与工作流 agent 各有自己的块，它们名下再派的子代理也跟着不进树。工作流的运行与阶段怎么记、`/flows` 怎么聚合见 [`workflow.md`](workflow.md) §9。

- **回调卡片**：终态回调（完成 / 失败 / 被停止 / 因重启中断，含子代理与团队成员的交付）在对话流里是一行卡片，写明哪个任务、什么结果、用时，与子代理自己写的话分开显示（DeepSeek 同样把这两类消息分成不同来源）。**周期提醒不出卡片**，`workflow_agent` 不出卡片（整次运行由 `workflow_run` 那一行代为说明）。数据流：回调消息（`customType: "yuanshu.subagent"`，模型看到的文字不变）多带 `details.job`（`JobSnapshot`：id / kind / name / label / ref / state / exitCode / startedAt / endedAt，不含完整命令与输出）；实时由会话流的 `notice` 事件（`{kind: "job", job, ts}`）下发（SDK 注入这条消息的 `message_end` 那一刻，位置就是它进入对话序列的位置），历史由 `GET /sessions/:id/messages` 的 `notices: [{afterIndex, ts, kind: "job", job}]` 给出；目标卡片走同一条路（`kind: "goal"`，见 `goal.md` §5）。**卡片不进消息下标**：对话消息仍只有 user / assistant，卡片按 `afterIndex`（该条目之前已投影的条数，与 `compactions` 同口径、`projectMessages` 与 `projectNotices` 共用「什么算对话」的判据）锚在消息之间；实时到达的卡片客户端按「此刻已有多少条消息」锚定，历史里同一张卡（key = `job:任务 id@结束时间`）到了以历史为准。
- **点开去哪**：子代理 / 团队成员去它们的 `sub` 标签；命令、工具开新的 `job` 标签（标签类型见 [`layout.md`](layout.md) §3），内容是完整命令 / 工具参数（`jobs.input`，最多 20000 字符，登记时存）+ 实时输出。`GET /jobs/:id` 给详情，`GET /jobs/:id/log?from=<字节偏移>` 给日志：不带 `from` 取最后 256 KB（起点对齐到行首，`headCut` 标「已省略更早的输出」），带 `from` 往后读（一次最多 1 MB，不在多字节字符中间截断），`next` 是下次该传的偏移，`ended` = 任务已是终态且已读到末尾（前端据此停止轮询）。
- **右栏「后台任务」块**：命令与工具（子代理有自己的树，工作流有自己的块，不列），**只列在跑的**，一结束就消失（结果去对话流里的回调卡里找）；行上状态点、简述、已用时，悬停出「停止」（二次确认，等同 `job_stop`），点开去任务标签。任务登记 / 结束 / 重开 / 改提醒时服务端发 `jobs.updated` 事件，右栏据此重取，不轮询；没有在跑的任务时整块不出现。
- 输入框的停止按钮：停那个会话的 agent 的运行。根 agent 不级联；**子代理标签里的停止就是停止这个子代理，按 S5 链式**，并回调给派发它的 agent。
- **子会话不进会话列表**（单列是污染）：不进左轨、不计入会话数，只能从右栏的执行体清单（子代理树、团队名册）进入 sub 标签。

## 10. 未实现与未决

- **可派发清单**（§7）没做：它要在会话弹窗里有选择界面，创建弹窗没有加（还没定它的形态）。现在 `agent` 参数可选任何 Agent 定义，内置段列出全部；「`spawn_subagent` 要求清单非空才声明」随它。
- **协作区没有界面入口**：右栏没有「附件」「协作区」分区（附件区也没有浏览入口）；设想的入口是聊天标签右侧栏里的分区，点文件沿用预览标签打开，子代理标签里显示同一棵树的协作区并高亮自己的子目录，默认收起、非空才显示、带数量。
- **运行视图的统一与审计页**：子代理树、团队名册、工作流的「运行 → 阶段 → agent」各是右栏里独立的块；三者要不要统一成一个视图、与审计页（审计页的「子代理」档读整棵子树）的关系，未定。左轨与底栏是否用一个计数提示「N 个后台任务运行中」，同样未定。
- **fork 的开场 user 消息**直接接在分叉点后面，可能 user 接 user 或工具结果接 user，各供应商的处理没有验证（只用 stub 与本地模型跑过）。
- **`executeTool` 在外层调用返回之后能否继续使用**：bash 已验证可以（`job/session.test.ts`：外层 `job_start` 返回后内层命令照常跑完、回调带着输出）；MCP 等其他工具走同一条路径，没有单独验证。
- **模式拦截里给协作区加看路径的例外**：模式的本意是「不改动项目环境」，不是字面只读，协作区在任何模式下可读写这条原则成立，但需要在模式拦截里加看路径的例外；没有真实需求，不做。

**设计参照**（对其他实现的调研）：回调唤醒与 steer、完成通知与子代理发言分开（DeepSeek harness）；停止不级联、关闭才级联、超限报错不排队（Codex）；fork 截点（DeepSeek 截在上一个完整轮次，会丢当前轮已读内容，Codex 保留 spawn 调用并补「aborted」，本文的截法两者都不同）；只读子代理的产物由运行时落盘、产物外置只回传引用（pi-subagents、Anthropic 多代理研究系统）。
