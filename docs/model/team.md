# 团队（agent teams）

Author: bluezeamer
Status: 现行
Date: 2026-11-03
Verified: 2026-11-19（对着代码核对：`team/{runtime,board,tools}.ts`、`store/baseline.ts` 的 `teams` / `team_members` 表、`api/team.ts`、`session/{aux,delivery,tool-catalog}.ts`、`changes/tracker.ts`、`subagent/{runtime,collab}.ts`）

多个子代理长期协作：成员有名字，可以主动互发消息，通过一块公告板同步决定与变化。**团队不是子代理的升级版，是在子代理之上加一层通信**，子代理本身（派发、限额、协作区、链式停止、交付）见 [`subagent.md`](subagent.md)。动态工作流是另一件事，不在本文。

## 1. 原则

- **T1 团队 = 一组有名字的子代理 + 成员间消息 + 公告板。** 成员就是子代理会话，沿用全部限额、协作区、链式停止与「没有审批通道」。只有 lead（与用户对话的根 agent）能建队；一个会话一个队；扁平，不嵌套，成员不能再建队。
- **T2 共享目录，不做隔离保证**（Claude Code 式）。lead 建队时把文件或子目录的划分写进各人任务，靠约定避免冲突。worktree 以后可作为可选项，不进第一版：非 git 目录与远程目录用不了。**成员不自己提交 git**（没有审批通道，几个人往同一棵树提交也会混），由 lead 看整体改动后提交。
- **T3 没有任务板，改用公告板。** 任务板是共享的可变状态，会引出抢占、过期、状态滞后；公告板只追加，没有这些问题。
- **T4 公告不推给 lead**，lead 只在需要时读板子；成员给 lead 的**私信**会推（用于架构决策、设计不合理处，讨论比直接做事有价值）。
- **T5 团队整体是一个能力单元**，开关只有一个，不细分到单个工具。

## 2. 工具面

| 工具 | 谁有 | 作用 |
|---|---|---|
| `team_create` | lead | `{members:[{name, agent, task, context?}], note?}`：建队并启动全部成员，同时发出首批公告（每条任务注明归属）。成员名在队内唯一、不可改 |
| `team_update` | lead | 增加成员；减少成员（**只能减没在运行的**，要先停） |
| `team_stop` | lead | `{member?}`：不带参数停整个团队，带成员名停单个成员；链式停止（成员名下的后台任务一并停）。**专门的团队工具**：控制粒度是团队与成员，不是 `job_stop` 的单个任务；底下是同一套链式停止 |
| `team_status` | lead | 每个成员的状态与最新交付路径，加板子摘要（调用辅助模型，§5）。lead 觉得该验收时自己取，不自动推送 |
| `team_disband` | lead | 解散：停止全部成员（链式），花名册清除；板子与成员会话保留，随根会话一起删 |
| `team_diff` | lead | 按需看团队整体改动：不带参数列出改动的文件，带路径看单个文件的 diff |
| `post` | lead 与成员 | `{text, to?}`：不写 `to` = 公告（推给所有成员，不推 lead）；`to` = 成员名或 `lead` = 私信（不进板子，推给收件人） |

- **成员各是一个子代理任务**（任务 id 就是成员会话 id），底层与存活数、深度、链式停止共用一份登记；**逻辑上区分**：lead 的 `job_list` 里团队只占**一行**（「团队：4 个成员，2 个在运行」），不逐个列成员，细节用 `team_status`；成员自己拉起的后台任务只在成员自己的清单里。对成员的编号用 `job_stop`，返回「这是团队成员，请用 `team_stop`」，保证每种东西只有一条停止路径。`team_create` 一次启动多个成员，**立即返回，不包进 `job_start`**（否则 job 清单里同时有「团队」与「成员」两套条目）。停止不等于移除：停下的成员仍在花名册里，被 `post` 唤醒后可继续；移除才是真的拿掉。
- 与 lead 对话仍可用 `message_subagent`，团队内统一用名字寻址的 `post`。
- `post`、`team_*` 与 `deliver` 一样，**走占位通道尾部注入**，不改声明、不动前缀（`prompt-delivery.md` §4）。
- 成员的 `read` 等普通工具由它自己的 Agent 定义决定；`post` 是框架工具（`prompt.md` E6）。

## 3. 公告板

- **是协作区里的一个只追加文件**，位于团队根目录（不在任何成员自己的子目录里），在虚拟主机 `collab` 里的地址是 `/board.md`。写入只能经 `post`，由框架完成：成员用 write/edit 改不了它（路径护栏拦）。
- **署名自动加**：`post` 没有署名参数，框架给每条加标题 `## #12 · 14:03 · backend → all`（编号、时间、署名、收件人）。**提示词里强调这个约定**：不要在正文里自己写署名或标题，避免格式漂移。
- **读**用普通 `read`（本来就有截断与行偏移），不另设读取工具。板子应简短，署名是为了让人去私信问细节；开场说明写明：板子只放影响他人的决定、变化、bug 与完成情况，细节放文件或私信。
- **改**：lead 追加随时可以；**修改已有内容只在全部成员停止时**，护栏据此放行 lead 的 edit。
- **推送走 steer**：运行中的成员在下一步前收到；空闲的被唤醒。**已交付的成员收到公告时，附一句英文：若不影响你的交付，只回复 `work done`；否则更新工作并重新 `deliver`**（以最后一次为准）。
- **初始任务也经公告板下发**：全员都看到全局，只做自己那份。所有成员的开场消息里，公告板初始内容部分逐字相同、只在最后一句写「你是某某」，缓存可以共享。
- 成员 `deliver` 时，框架自动在板子上记一条「某某已交付：摘要」，不需要成员再发。

## 4. 完成、交付与汇总

- **`deliver` 是缓存区**：可以多次调用，后一次覆盖前一次，以最后一次为准。被唤醒后，本轮结束时要么重新 `deliver`，要么只回复 `work done`（忽略大小写、首尾空白与标点）表示对交付没有影响，沿用上一次；两者都不是，按 `subagent.md` §5 的方式提醒。
- **团队完成 = lead 宣布**：团队的目标是 lead 的目标，只有它知道是否达成；成员只能说「我做完了」。三家主流实现也都靠 lead 自己判断，没有机制（Claude Code 在文档里承认 lead 会提前收工、成员会提前停下，靠 hooks 打回）。
- **每个成员的交付单独回调 lead**，与普通子代理一样，一条一条到；没有「全员交付才汇总」的状态机。成员更新交付（被 lead 私信追问、被公告唤醒后改了东西）也照常回调。异常退出立即通知，提醒时间照常。
- **整体验收由 lead 用 `team_status` 拉取**：每人状态与交付路径，加**省流的板子摘要**。
- **板子摘要由一次轻量的单独调用生成**，用「辅助模型」（§5）：输入是整块板子，输出是决定、变化、bug、未决问题的要点；调用失败就附最近 20 条原文并注明摘要不可用。
- **`team_diff` 不注入**，lead 按需自己查。建队时拍一个基线，复用轮末改动的机制（`changes/tracker.ts` 的 `ChangeTracker`：git 目录用临时索引存目录树，非 git 目录记录 write/edit 前后的内容）。限制：非 git 目录里 bash 造成的改动看不到。

## 5. 辅助模型（新增的全局设置）

- 用于一次性的小调用：板子摘要；以后做会话自动命名也用它。放进设置页「默认值设置」。
- 没配置时用当前会话的模型，开箱可用；配了就用配的，建议选便宜的。
- 与「审核模型」（审批用，`prompt.md` P5）是两个独立设置，选择方式一致。

## 6. 生命周期

- 可以建、解散、加成员、减成员（只能减没在运行的）、追加公告、改公告（只能全员停止时）。
- **不主动删除**：停着的成员不占「最大存活」名额，板子是个小文件，随根会话一起删。
- 成员有名字，被 `post` 唤醒时沿用自己的上下文；lead 想进一步了解情况就私信成员。

## 7. 未实现与未决

- 公告的频率只靠文案约束，不设机制；真刷屏再加。
- 每条公告会唤醒所有已交付的成员，各花一次很短的调用（缓存通常还在），团队只有三五个人时可接受。
- 成员发现 lead 的划分有冲突时怎么办：私信 lead，讨论胜过直接做。
- `work done` 是文本约定，靠规范化比较；真漂移再改成工具调用。
- worktree 作为成员可选项：有 git 的目录才可用，以后做。
- 建队时 lead 的未提交改动、成员的开发服务器端口冲突，只靠任务说明里写明，不做机制。
- 停着的成员是否常驻内存取决于会话池现有策略，没有核实。
- 成员在团队目录之外的 directory 里的写入不进 `team_diff`。
- **已知限制**：被唤醒的轮次若被停止或失败，`team_status` 里该成员此前的交付摘要被覆盖成 stopped / failed（交付已回调 lead、报告文件还在）；成员顺序启动，启动窗口内别人发的公告后启的成员既没在开场消息里也没被推送；`team_update` 加的成员开场消息内嵌整块板子。

## 8. 实现要点

服务端在 `team/`（`runtime.ts` 运行时、`tools.ts` 工具、`board.ts` 公告板、`messages.ts` 文案、`view.ts` 任务清单视图）与 `store/teams.ts`（表 `teams`、`team_members`）。成员走 `SubagentRuntime.launch()`，与普通子代理共用同一条派发路径（建会话、登记任务、限额、协作区、链式停止、交付），团队只加花名册、`post` 与板子。要点：

- **工具**：`team_create / team_update / team_stop / team_status / team_diff / team_disband` 六个，合成能力单元 `unit:team`（服务端 `CAPABILITY_UNITS`、Studio 与创建面板共用的 `web/src/api/capabilities.ts` 各一份镜像）；`post` 是框架工具，**只有有队的 lead 与队员才有**（`DeliveryHost.canPost`），建队后经状态通知出现，不改冻结声明。所有会话都注册这些工具的声明（冻结声明才能与 lead 逐字节相同、共享缓存），谁能调用由运行时判断：只有根会话（非子代理）能管团队，成员调用会被告知「你是子代理」。
- **成员即任务**：登记成 `kind=subagent`、`name=team_member`、标签为成员名的任务（任务 id 还是成员会话 id）。lead 的 `job_list` 里这些行不列，团队占一行「team: N members, M running」；对成员用 `job_stop` / `job_remind` 被拒并指向 `team_stop`，`message_subagent` 被拒并指向 `post`。成员的交付、失败、停止回调文案称「Team member 名字」，联系方式写 `post`。
- **板子**：协作区（虚拟主机 `collab`，SSH 目录上的成员也读得到）里团队根目录下的 `board.md`，地址是 `host="collab", path="/board.md"`；`post` 与建队由框架加 `## #12 · 14:03 · backend → all` 标题；成员交付时框架自动记一条「Delivered: 摘要」（`work done` 不记）。lead 在**全部成员都没在运行**时可以直接 `edit` 它（`CollabArea` 的 `canEditBoard` 谓词，只放行这一个文件）；成员写它走普通判定，无人值守时被拒。建队时按顺序写入：可选 `note`，再每个成员一条任务。新队接手一个已有旧板子的会话时，旧板子改名为 `board.1.md` 保留。
- **推送**：公告推给除自己外的所有成员（不推 lead）；私信推给收件人，成员给 lead 的私信用 steer 推。运行中的成员 steer，已交付的唤醒并附 `work done` 约定，**停止或失败的成员不被公告唤醒**（返回里列出「未通知」，它们下次运行时自己读板子）；lead 私信停止的成员会唤醒它。公告与成员之间的私信引起的唤醒是静默的：成员只回 `work done` 就不回调 lead；它改了交付重新 `deliver`，或 lead 自己私信引起的唤醒，照常回调。
- **开场消息**：所有成员除末尾「You are "名字"」与自己的目录两行外逐字相同，含初始公告板全文（测试断言）。
- **限制**：成员名 `^[A-Za-z][A-Za-z0-9_-]{0,31}$`，不分大小写不重名，`lead` / `all` 保留；一条 `post` 最多 4000 字符；整批成员放不下存活上限（`SubagentRuntime.ensureRoom`）就一个都不启动；一个会话一个队，`team_create` 在已有队时报错。
- **辅助模型**（§5）：设置页「默认值」有「辅助模型」一节（`auxModel`，选法与审批模型一致，各自独立）；`session/aux.ts` 的 `createAuxRunner` 每次现读配置，没配就用调用会话此刻的模型，超时 60 秒；与审核会话共用 `session/one-shot.ts` 的一次性会话构造。`team_status` 的摘要失败或超时就附最近 20 条原文并注明。
- **`team_diff`**：建队时用 `ChangeTracker.begin` 拍基线（键 `team:<lead 会话 id>`）。git 目录对比建队时的目录树，连 bash 造成的改动也看得到；非 git 目录只记录 lead 与成员**在团队目录里**的 write / edit。不带参数列文件（A/M/D 与行数），带路径看单个文件 diff（相对路径或目录内的绝对路径，上限 6 万字符）。`ChangeTracker.noteWrite` 按键排队，几个成员同时写不会互相覆盖 `meta.json`。解散或删除 lead 会话时清掉基线。
- **重启与删除**：Server 重启时在跑的成员记为中断（与子代理一致），花名册保留，成员显示为 stopped，被 `post` 唤醒后可继续。删除成员会话时把它从花名册去掉；删除 lead 会话时花名册、板子（随协作区）与基线一起清掉。
- **界面**：右侧状态的「团队」块有名册（来自 `/flows` 的 `source: team`）、公告板一行与团队改动一行；后两行取自只读接口 `GET /api/v1/sessions/:id/team`（公告板条数、最近 3 条、文件路径，建队以来的改动文件）与 `GET /api/v1/sessions/:id/team/diff?path=`（`api/team.ts`，复用 `TeamRuntime.changeSet / fileDiff`，与 `team_diff` 同一份数据）。成员的会话由 `/flows` 给，点名册一行开成员会话。

测试：`team/team.test.ts`（建队与交付、公告与私信、停止与成员管理、限制、`team_diff` 的 git 与非 git 两轨）、`team/team.server.test.ts`（真实服务 + 真实会话工厂：`post` / `deliver` 在无人值守的成员里可用、辅助模型的取用与回退）、`test/live/team.live.test.ts`（本地模型：建队、两个成员读文件、发公告、交付、lead 拿到两个暗号）。

**设计参照**（对其他实现的调研）：Claude Code 团队（共享目录、人划分文件、邮箱、不嵌套）；DeepSeek harness 的设计笔记（明确否决把任务归属当锁，理由是假的互斥比明确的警告更危险；成员消息就是写进对方输入队列）；Codex（共享目录，要求各任务写集不相交）；Anthropic 的结论是编码任务真正可并行的部分比想象的少，团队更适合读多写少的协作。
