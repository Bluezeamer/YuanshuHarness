# 基于 Pi 二次开发的定制化 Agent：初步构想

## 一、核心底座需求

### 1.1 稳定的 Server–Agent 核心

- **进程级持久化**：Agent 作为后台服务运行，UI 客户端断开后不影响任务执行。
- **崩溃恢复**：Server 重启后，Session 状态可恢复，任务不丢失。
- **基于成熟 API**：使用 `pi-coding-agent SDK` 层（openclaw已有实践），不依赖实验性的 `pi-client` / `pi-server` 远程协议。
- **持久化范式对齐 Pi Durable**：Pi 1.0 同期发布的实验包 Durable 已验证"检查点化执行"范式（每步模型/工具调用落检查点、崩溃/重启后续跑、多会话并行）。本项目 Server 的持久化设计借鉴其范式，但对其 API 收敛在内部接口之后，不深度绑定（Durable 仍标记实验性，成熟设计预计回流 Pi 本体，届时整体替换）。

### 1.2 统一 Session 层

- **单 Session 多客户端**：同一个 Agent Session 可同时被 TUI、WebUI、IM Attach。
- **状态一致性**：所有客户端看到的事件流都来自同一源头，不存在“IM 的 Session”和“TUI 的 Session”各自独立的问题。
- **交互统一路由**：`confirm`、`select`、`input` 等对话框通过统一总线分发，采用 **First Response Wins**（第一个响应生效）策略。
- 分层原则与 Durable 的多客户端接入模型同源：**会话状态与传输分离**——状态管理不假设任何单一客户端连接存在。

### 1.3 凭证体系：集中网关 + 一次性能力票（雏形）

> 2026-10-07 于 bookmarkAsNewtab 接线讨论中收敛。核心问题：agent 调用外部资源（模型 / GitLab 等）时用什么凭证？
> 收敛结果：**agent 只见一次性能力票，真 key 由集中网关持有并转发——无感，用完即销毁。**

- **角色（只有两个）**：
  - **集中网关**（常驻，一台机器，如 GitLab 同机 LXD）：持有所有真长期 key + 自身签名钥；职责 = ① 一次性 key 生成与分发 ② 集中转发（真 key 只在网关内附上）。
  - **Agent / Job**（每任务）：只持一次性能力票 C；正常调用，对“真 key”的存在零感知。
- **一次性票 C**：job 开始向网关 `/mint` 出示 job 身份（如 CI_JOB_TOKEN）换取；绑定本 job、短 TTL、用完即销毁（job 结束即过期；进一步可选：任务完成钩子触发即时销毁）。
- **无感**：agent 侧唯一配置变化 = `baseUrl` 指向网关 + `apiKey = C`（pi 的 openai-completions 协议天然兼容，零代码改造）；agent 的 egress 只放行网关，到不了模型提供商 / GitLab 直连。
- **为什么安全**：C 是“能力”不是“凭证”——只对本 job、对指定端点、短命有效，被提示注入偷走 ≈ 废纸；真 key 只存在于网关进程内存，不进 runner / agent、不进日志 / diff；信任锚从“不可审计的 LLM”迁移到“可审计的确定性网关代码（百行级，可人审）”。
- **注意项（实现时红线）**：
  - 网关是最高价值目标：VM 隔离 + 网段限制 + key 从加密存储加载（不落明文文件）+ 全操作审计 + key 轮换 runbook（练到 10 分钟）
  - C 无状态（HMAC 签名，验签名+过期即可，无数据库）→ 需要时加副本横向扩
  - 网关可见全部 LLM 流量 = 审计 / redact / 成本统计的落点
  - 残留风险（已接受）：网关宿主机被破 = 全部 key 一次泄露——Vault 立论：防护良好的集中库胜过散落各处的 key
- **范围与边界**：先 LLM key（当前重点）；GitLab 评论 / push 等其他特权通道后续同模式，统一收口到网关。阶段 1 现状（qwen 端点无 key、key 直接放 CI 变量）作为过渡可接受；本节为雏形记录，暂不排期实现。
- **内侧对应物**：网关管"对外调用的凭证"；harness 本机侧的隐私变量（ssh-key、sudo 授权、各类 token）由 3.4.2 的隐私变量库承接，两者共用遮罩与审计纪律。

## 二、客户端形态与分工

### 2.1 TUI：CLI 环境的 Agent 可达路径

**适用场景**

- SSH 连接远程服务器。
- 无图形界面环境。
- 快速终端操作。

**主要职责**

- 轻量交互。
- 代码编辑。
- 实时流式输出。

**要解决的痛点**

tui形态下部分操作比较麻烦，比如对于对话历史的快速翻阅跳转等；这一点的解决方案不在tui内，而通过webui形态来进行相关体验的补充。

### 2.2 WebUI：深度管理与远程查看

**适用场景**

- 通过本地浏览器远程连接。
- 多 Session 总览。
- 详细审计。

**主要职责**

- 查看所有对话历史、执行细节及工具调用链。
- 修改设置，包括模型、参数、权限策略等；图形化操作比 Slash Command 更友好。
- 管理多个 Session 的生命周期，包括创建、暂停、恢复和归档。
- 内置渲染面：浏览器页面预览与典型格式文件预览（pdf/html/md 等，见 3.4.3）。

**关键能力**

Server 在后台运行期间，WebUI 可以随时打开并查看任务进度，不需要始终保持长连接。

### 2.3 IM（QQ / Discord 等）：即时通知与轻量任务

**适用场景**

- 移动端使用。
- 团队频道协作。
- 异步通知。

**主要职责**

- 接收 Agent 的任务完成、需要审批、异常等通知。
- 派发临时轻量任务，例如“帮我查一下这个 Bug”“总结一下刚才的提交”。
- 完成简单的确认或拒绝交互。

**要解决的痛点**

当前 OpenClaw、Hermes 等工具主要解决了“接入”问题，但没有提供较为方便直接的入口来查看完整对话细节，且这种助手往往系统提示词过于重，承载的功能过于冗杂繁复。因此这里希望根据个人需求高度定制化。

> 与 3.3 的关系：IM 助手“提示词过重、功能冗杂”的痛点，在能力特化框架下不是需要单独优化的问题——助手 Agent 默认就应运行在一个极窄的静态能力预设上（无 bash、无文件写、仅少量只读 Skill），这是同一机制的自然应用而非特判。

## 三、Agent 能力扩展需求

### 3.1 特化 Coding Agent

**目标形态**

打造类似 Claude Code、但能够根据个人偏好进行高度定制的 Coding Agent。

**强化能力**

- **Subagent**：将任务拆解委派给专用子代理处理，以节省/避免污染主agent的上下文。管理者是主agent，subagent之间无法通信。
- **Agent Teams**：形成多个agent实例，通过看板领取分发任务，通过邮箱系统相互沟通，来全面高效的完成审计或者复杂开发任务。至少能对抗：1. 单agent可能形成的遗漏 2. 单agent可能形成的思维惯性。**这些好处源于：subagents形成team，之间可以相互通信，而不必通过主agent做间接沟通。**
- **Dynamic Workflow**：类claudecode的dync-workflow设计，实现针对不同任务特化的由agent自编写的agent编排调度流水线。操作的最小单位是一个agent实例，通过编排不同阶段不同agent的任务以及发起的agent数量（这里可能涉及到的编排模式就是 pipeline | fan-out/fan-in | supervisor）以及任务控制流程，来实现一复杂任务的实现。这与agent-teams的不同点在于，一个主agent完成了总体流水线的预编排再进入到具体的任务执行，而非基于teams的任务领取与通信来完成。这里的对抗与检查就是有目的性的行为，例如主agent通过并发拉起两个subagent，一个负责完成一个负责检查，来完成显式的补漏或是对思维惯性的纠偏。**此设计一个更为直接的原因和目的是：当整个流程过于复杂需要设计到前后链路较多数量的agent管理和编排时，仅靠主agent自身的记忆去完成调度编排本身是不可靠的，且会很大程度上污染主agent的上下文。而预编排的调度流一定程度上解决了这个问题，主agent只需要接收最终的结果即可。**

> 与 3.3 的关系：上述三种多 agent 机制在派发子代理时，均可叠加动态能力裁剪（见 3.3 路径二），使被编排的每个 agent 实例在能力层面同样聚焦，获得更好的任务完成质量。

> 与 pi 1.0 codemode 的关系：pi 1.0 的 codemode 实现了**工具粒度**的脚本化编排（模型在 QuickJS 沙箱中写 JS 编排 MCP 工具调用），与本设计的 **agent 粒度**编排是上下两层互补关系。设计时显式利用这一分层：编排脚本只管 agent 生命周期，被编排 subagent 内部的 MCP 密集任务交给 codemode；不把工具级逻辑抬进 agent 编排层。

### 3.2 特化助手 Agent

**目标形态**

面向个人或团队的智能助手。

**主要能力**

- 被动响应 IM 消息。
- 主动推送状态变更通知。
- 与 Coding Agent 共享同一核心，避免形成“两个独立系统”。

### 3.3 能力特化：可插拔能力集设计

**核心概念**

为 Agent 新增可插拔的能力设计：能力（内置工具、Skill、MCP 能力等一切以标准方式接入 Agent 的能力）全部原子化，通过预设的能力集合进行组合。针对不同需求，在选定的能力集合中激活特定能力即可。

本体论上是**注入**而非裁减：Agent 从零能力开始，按需注入；“全集”只是恰好什么都注入了的特例。默认全集正是上下文污染与安全面过大的根源。

与 Skill 的区别：Skill 是渐进式提示词（知识）设计，解决“agent 知道什么”，其工具通常以 CLI/脚本形式经 bash 调用，不占用 tools 槽位；能力集解决“agent 能用什么”。当 Skill 目录堆到上百条时，仅靠渐进披露仍会出现工具选择困难——无关 Skill 与工具会对注意力形成污染和干扰。能力集是对选择空间的直接缩小，与 Skill 是正交互补的两条轴。

由此形成三轴正交的特化框架，一个 Agent 实例的完整定义为 `提示词 × 能力集 × 知识集 × 协作拓扑`：

| 轴       | 机制                                             | 回答的问题     |
| -------- | ------------------------------------------------ | -------------- |
| 结构特化 | Subagent / Agent Teams / Dynamic Workflow（3.1） | 任务怎么分工   |
| 能力特化 | 能力预设 + 动态裁剪（本节）                      | agent 能用什么 |
| 知识特化 | Skill 渐进加载（扩展生态）                       | agent 知道什么 |

**设计收益**

- 统一安全边界与注意力聚焦：能力在不在场是同一个操作。物理上不存在的工具，既是绝对的安全边界（强于门控——门控后的工具仍在上下文中，可能被说服或绕过），又是绝对的注意力聚焦（选择错误概率从源头归零）。
- 预设能力集与 Skill、提示词一样，是可版本化、可分发的资产（例如“审计员 = 只读工具 + 代码检索 Skill + 对抗检查提示词”）。
- 不同需求的 Agent 直接通过预设特化能力倾向，保持上下文高度聚焦。

**两条裁剪路径**

1. **静态预设**：用户通过设置主动裁减出特化能力的 Agent。除工具/Skill/MCP 的白名单外，还可包括系统提示词的替换或追加的 AGENTS.md。
2. **动态裁剪**：主 Agent 在派发时动态裁减 Subagent 的能力，使其能力与注意力聚焦，获得更好的任务完成质量。裁剪决策可由一个临时的预分析模型做出（类似 Claude Code auto mode 的分类器策略；实现可挂 pi 1.0 的 virtual models 机制，用独立小模型承担）。注意错误代价不对称：auto mode 误判的代价是一次多余确认，裁剪误判的代价是子任务链的隐形低质——因此预分析模型应**系统性偏宽**，宁多给三个无关 Skill，不可少给一个关键工具。

**范例：plan mode 即组合**

plan 模式无需更复杂的拦截设计（cc/opencode 中通常原生耦合的权限设计），只需 `[plan 模式所属的特定提示词注入] + [裁剪出的只读能力注入]` 即可完成，甚至无需工具权限门控或额外设计。这印证了：**“模式”应当是原子能力的涌现组合，而非硬编码的系统特例。**（第二个组合范例见 3.4.1 的 sudo 提权。）

**工具加载的三层结构（缓存感知设计）**

前缀缓存的事实约束：模型服务端按**前缀内容哈希**判定缓存命中，与 session-id 无关；请求序列化顺序为 `tools → system → messages`，工具 schema 位于前缀最前端，**任何对 tools 列表的运行时改动都会使其后全部缓存失效**。因此能力注入必须以“tools 数组永久冻结”为前提，按以下三层组织：

1. **主干能力：原生预声明（首选路径）**。派发时由静态预设/预分析模型把该 Agent 所需工具**尽量覆盖地**直接注册进 tools 数组，使用强类型 schema（调用质量最高）。分配标准：高频且参数复杂的能力（read/edit/bash 等）必须走此层。tools 数组在会话创建时一次性确定，此后不再变更。
2. **长尾能力：延迟加载保底（常规兜底）**。优先复用 **pi 1.0 核心的 deferred tool loading**（工具定义不渲染进上下文，发现后于末尾注入），外层包能力注册表提供白名单权限语义。注意语义分层：deferred loading 解决“工具太多装不下”（注意力/经济），白名单解决“这个 agent 不许用”（安全边界）——未授予的能力即使被发现，调用时也直接拒绝。若官方实现语义不足，退回自建网关元工具方案（`search_tools`/`describe_tools`/`call_tool`，schema 冻结；告知模型正确 schema 的场所是 tool result 而非提示词；提示词仅需一条冻结纪律“先 search、再 describe、后 call”）。MCP 能力经 pi 1.0 codemode 原生通道接入，被同一白名单覆盖。
3. **能力升级通道：仅作最后手段（保留设计，不作常规路径）**。当前两层确实无法覆盖（如任务中途出现结构性阶段切换、需要从只读升级为可写）时，Subagent 可结构化地向主 Agent 申请能力（“我需要 X 完成 Y，因为 Z”），裁决走统一交互路由总线（与 confirm 同一条 First Response Wins 路径）。实现优先走 **pi 原生 mid-conversation 工具/提示词变更**（transcript 追加系统消息式注入，带缓存前缀保护）；该能力模型相关，以模型目录标志位（`supportsMidConvoSystemMessages`）探测决定走原生还是回退路径（回退=重建工具集，接受一次性前缀重写，或经代理工具读运行时注册表）。**设计取向上应尽量避免走到此层**：裁剪失误的代价是子任务链的隐形低质，而升级通道的存在不应成为前置裁剪偷懒的理由——预分析偏宽取向（见路径二）与延迟加载兜底已能覆盖绝大多数情形。

**边界与约束**

- **原子性下限**：可拆能力（read_file/write_file/edit）适合注入式裁剪；但 bash 是不可拆的原子巨兽（同时是只读工具和全能武器），无法被“裁剪成只读”。因此门控层无法被消灭，只能被压缩：可拆能力走注入/裁剪，不可拆原子能力保留一个薄门控层。两层显式分层，不假设裁剪覆盖一切。
- **动态裁剪的静默失败风险**：预分析裁错时，Subagent 不会报错，只会在能力不足的条件下交付看似完成的低质结果——比显式失败更危险。三层结构是对该风险的主防线（延迟加载保底使“缺能力”大概率表现为一次发现即可补救的小事），升级通道是最后保险。
- **白名单优于黑名单**：黑名单会随生态扩展持续漏（新接入的 MCP 默认放行是危险默认值），白名单的默认态是安全的。
- **可观测**：WebUI 应能查看每个 Session/Subagent 实际激活的能力集（含各工具所处的加载层），作为“详细审计”职责的延伸与调试低质子任务的第一手信息。

**实现依据（Pi 1.0 SDK 原语映射）**

该设计位于 SDK 层之上，无需 fork，与第四章的稳定性与渐进式约束无冲突（2026-10 起 pi 1.0 已定版，SDK/扩展 API 宣告稳定）：

| 设计机制                    | Pi 1.0 对应原语                                                                                                           |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 内置工具白名单裁剪          | `createAgentSession({ tools: [...] })`，默认即最小能力面                                                                |
| 长尾延迟加载                | 核心 deferred tool loading（1.0 原生），外层包能力注册表白名单语义；不足时退回自建冻结 schema 的网关元工具（customTools） |
| MCP 能力接入                | 1.0 codemode（QuickJS 沙箱，模型写 JS 编排 MCP 工具），与 deferred loading 组合                                           |
| 系统提示词替换/追加         | `systemPromptOverride` / `appendSystemPromptOverride`                                                                 |
| Skill 集裁剪                | `skillsOverride`（ResourceLoader 级，按能力预设构建 loader 实例）                                                       |
| 薄门控层（bash 等原子工具） | `tool_call` 事件拦截 `block`；bash 另有 `spawnHook` 可改写命令、强制 cwd/env                                        |
| 动态裁剪的预分析模型        | 1.0 virtual models（独立小模型承担决策/核验），或派发前一次 `createAgentSession` 参数计算                               |
| 升级通道（末位手段）        | 1.0 原生 mid-conversation system prompt / tool changes（带缓存前缀保护，按模型标志位探测）                                |

需自行补齐的缩减为三样：能力清单元数据（名称、类型、只读性、互斥/依赖、所处加载层）、预分析模型的裁剪决策、能力注册表（白名单语义）。网关三件套仅在官方 deferred loading 语义不足时补缺。

### 3.4 生产级原生能力

> 定位：以下能力多数以插件/skill 形态零散存在，但"原生好用"要求它们由持久 Server 持有状态、被统一总线与能力集体系覆盖。统一原则沿用 remote-ssh 的设计哲学：**差异注入到尽可能低的层，上层结构同构**。

#### 3.4.1 执行环境扩展线

- **原生 remote-ssh**：以 ssh-harness 项目（`docs/design-remote-ssh-pi-harness.md`）为蓝本，Connection Manager 从 per-session 插件资源**升格为 Server 级服务**——持久 Server 维持 ssh 连接通道（心跳/断线重认证/通道多路复用），Session attach 时挂载目标主机；凭据存隐私变量库（3.4.2），模型不可见、不入 transcript；多 host/连接池因 Server 天然长寿而从原 v2 提前纳入。模型无感（原生工具面同构）、人类透明（环境行）、围栏三层分明（结构化硬约束 / bash advisory / 部署前提）等已验证设计全部沿用。
- **sudo 提权工具**：不造子系统，复用组合——`薄门控层（tool_call 拦截识别提权命令）+ 统一总线 confirm 弹窗（First Response Wins）+ 隐私变量授权（用户手动输入或引用 @变量代填）`。sudo 密码永不进 transcript/日志。这是"plan mode 即组合"之外的第二个组合范例，再次印证"模式 = 原子能力组合"。
- **持久进程追踪（后续实施）**：harness 部署的内网持久服务由 Server 登记并追踪。被动：心跳巡检登记进程；主动：端口可达性探测，联动内置浏览器（3.4.3）一键访问。参考 codex app 的内置浏览器形态。

#### 3.4.2 信任与凭证线（与 1.3 互为内外侧）

- **隐私变量管理**：Server 级加密存储 key/token/ssh-key 文件等，配套工具：`list`（列出变量名与元信息，不含值）、`@变量` 引用注入。核心机制为**双向字符串匹配遮罩**：注入 harness 的上下文中凡匹配到与隐私变量一致的内容，即以 `sk-xxx(已隐私加密)` 形式替换呈现——兼顾格式可读性与安全性，且在强制围栏约束下被越狱查看的概率小；遮罩与 1.3 网关侧的 redact 审计落点对称。ssh 连接所用校验文件同库存储（与 3.4.1 联动）。相比让 harness 读 env/配置文件（需额外交代文件格式），以 harness-bash 工具直接翻译引用更简洁，且用户可跨会话统一管理。
- **autoapprove 核验模型**：参考 codex 的 auto-approve——大量命令不必人工逐一校验，由核验模型代审，人工只处理例外；降低开发者决策疲劳。定位为 3.3 路径二预分析模型的同族（实现挂 pi 1.0 virtual models，可用独立小模型）。**硬性边界**：sudo 提权、隐私变量注入、写豁免类操作永不走 autoapprove，必须人工确认。

#### 3.4.3 统一呈现线

- **内置浏览器**：一个核心、两个视角。harness 侧：页面校验测试、内网服务访问（联动进程追踪）；用户侧：WebUI 内嵌打开页面预览。浏览器会话状态由 Server 持有，客户端断开不中断——与 Session 层的"状态与传输分离"同原则。
- **UI 文件预览**：pdf/html/md 等典型格式的 WebUI 内置预览，与浏览器预览共用渲染组件；TUI 侧按优雅降级原则处理（复杂渲染件在 TUI 劣化或不可渲染，见"未竟事宜"）。

## 四、架构非功能性需求

| 维度               | 要求                                                                                                                                                                                                                                   |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **稳定性**   | 依赖 pi ≥ 1.0（2026-10 定版，SDK/扩展 API 宣告稳定）并 pin 版本；Pi Durable 相关能力按实验性对待（接口隔离、成熟回流后替换）；升级时重点回归 codemode/MCP 行为（该线打磨时间短）。版本下限含安全注记：0.78.1 起修复扩展加载相关 CVE。 |
| **可扩展性** | 享受 Pi Extension 生态，包括 Tools、Skills、Commands、Hooks 等；TUI 专属扩展在 Headless 模式下应能够优雅降级。                                                                                                                         |
| **不 Fork**  | 基于 SDK 嵌入，而不是修改 Pi 源码。                                                                                                                                                                                                    |
| **渐进式**   | 可以在一个稳定的基础上基于充分暴露的接口渐进式的根据需求实现各种功能。                                                                                                                                                                 |

## 五、一句话概括

一个基于 Pi SDK 构建的持久化 Agent Server，同时承载 Coding Agent 和助手 Agent；TUI、WebUI、IM 三种客户端共享同一 Session 池，各自负责最适合的交互场景，并且任意客户端都可以随时断开或重连，而不会中断后台任务。

## 六、未竟事宜

> 关于具体特性实现接入层面的思考

- 某些feat如果刚好落在插件范围里, 可以考虑直接做成插件部分, 这样有助于充分的生态兼容性; 当然只有部分可以做, 比如命令审计等; 而核心的CS架构等实现, 则必须介入sdk。不过坏处在于耦合度过低的情况下，部分功能的原生webui体验可能就会不太好，这里就需要同时维护两套ui展示逻辑：webui/tui。不过这部分有待商榷，也许可以通过预定义一些核心组件来达到基本的体验等同。例如codex-tui和codex-app的设计，codex-tui中基本组件的交互操作（e.g. 给出多选选项、ask-question等），这都是预定义的组件，是可以做到webui和tui的统一的；而某些部分则不行，比如mermaid或者更加复杂的显示组件，在tui上可能是劣化的或者完全不可渲染的（比如内嵌html页的渲染预览等功能）
- 3.4 各特性的插件/SDK 归属：remote-ssh 项目已验证执行面扩展可作为纯项目级扩展跑通，故 3.4 中各特性优先做成扩展形态；仅需 Server 级持有的部分（连接管理器升格、隐私变量库、浏览器会话、进程登记）进 SDK 层。插件形态的另一红利：可分发兼容纯 pi CLI 用户。

> 一些零散idea(可能与已经记录的部分有重复, 这里类似便利贴, 贴了一些各种来源的灵感和想法)

* 具备文件区的实时查看和预览功能，至少支持pdf、office格式文件、md等常见文档格式的文件
* 具备侧边虚拟浏览器的功能，以便快速划选提问、截图提问等
* 类似claudedesign的模式, 可以方便的进行快速前端和交互设计
* 布局设计：输入框与ai的输出内容错开形成差分显示，或者输入框的内容始终保持（尤其是TUI），原因在于经常性的需要滚动查看历史内容，同时进行输入，此时若输入框会被冲掉，那效率和连续性就会变差
* idea便利贴，以块形式组织各种思路，可以自由组合拼接
* 应用形态常驻一些链接，原生的webui自写应用，实现应用自由，有点类似cherrystudio的思路，但是更加优雅
* 具备快速跳转对话的能力, 以用户输入为节点快速跳转, 在页面的右侧可折叠, 类似kimi的在线chat版本那种
* 模型调用应该是可以动态指定的，对于pi正式版来说，就是virtualmodel了可能，典型场景是 调研 审计 等任务用不同的模型（甚至不同供应商的），达到效率和性能的平衡
* agent 隔离环境 workspace。agent指的是由提示词和工具集定义的一个agent；workspace指的是一个项目目录，agent以此作为cwd进行工作；隔离环境指的是agent处于的宿主环境，所有的修改仅限于此隔离环境，不外扩。因此，这里需要有相应的管理手段，来管理不同的 隔离环境/agent。workspace则是派生在隔离环境下的某个目录。
