# ADR-0019: 发布物的形态：命令名、npm 包结构、镜像基础与构建方式

状态：已定稿
日期：2026-10-17
可逆性：难逆
取代：无
被取代：——
引用入口：ARCHITECTURE「技术选型」发布物形态一行；ROADMAP 第 1 条

## 背景
[ADR-0012](0012-delivery-form.md) 定了交付物是 npm 包加 Docker 镜像，数据放进单一数据目录，
但没有定命令名、npm 包的结构、镜像的基础与构建方式。
这些一旦被使用者的脚本、Docker 配置和文档引用，改动就是破坏性变更，所以难逆。

约束：
- 开发期只在本地构建，不发布、不推送（[ADR-0012](0012-delivery-form.md)）。
- Node 下限 22.19（[ADR-0013](0013-tech-stack.md)）；Server 以 Linux 为目标。
- 以后要有命令行客户端（ROADMAP 第 3 条），不能让今天的命令写法挡住它。
- 两种发布物应来自同一份构建产出（[ADR-0012](0012-delivery-form.md)）。

下面提到的 Node 版本阶段与官方镜像情况，来自 2026-10-17 由 pi 做的网络搜索，
它没能直接抓取 nodejs.org 与 Docker Hub，且 Node 22 的结束支持日期各来源不一致，未经独立核实。

## 候选方案
### 命令名与启动方式
- A. 一个命令加子命令：`yuanshu serve` 启动服务，以后客户端用其他子命令。代价：多一个固定的 `serve`。
- B. 一个命令，不带子命令直接启动。代价：以后加客户端时裸命令的含义要变，会破坏 Docker 入口与使用者脚本。
- C. 两个命令：`yuanshu-server` 与 `yuanshu`。代价：两个入口要维护。

### npm 包结构
- A. 只发布 server 一个包，构建时把 web 产物复制进它的目录，web 包不发布。代价：构建多一步复制。
- B. 发布 server 与 web 两个包，前者依赖后者。代价：版本号要同步，发布两次。
- C. 用打包器合成单文件。代价：后面的 SQLite、pi SDK 若带原生依赖，容易出问题，报错栈也更难读。

### 镜像基础
- A. `node:22-slim`。代价：Node 22 在维护期，多数来源写结束支持约在 2027-04，约半年后要再升一次。
- B. `node:24-slim`。代价：我们的 CI 目前只在 Node 22.19.0 上跑，pi SDK 在 24 上是否正常未验证。
- C. `node:22-alpine`。代价：用 musl 而非 glibc，原生依赖容易出问题。

### 镜像构建方式
- A. 多阶段：第一阶段构建并打出 npm 包，最终阶段在干净的基础镜像里只装这个包。代价：Dockerfile 较长。
- B. 单阶段。代价：镜像带源码与开发依赖，体积大，多出攻击面。
- C. 直接复制宿主机上已构建的产物。代价：镜像构建依赖宿主机状态，本地与 CI 可能不一致。

## 决定
**命令名**：方案 A。命令为 `yuanshu`，启动服务写 `yuanshu serve`；
裸命令 `yuanshu` 不启动服务，其余子命令留给命令行客户端。
[ADR-0018](0018-startup-params-and-health-endpoint.md) 的参数写法不变，使用时写作 `yuanshu serve --host ...`，该 ADR 没有规定命令名，无需修订。
npm 包名到首次发布时再定，它可以与命令名不同。

**npm 包**：方案 A。只发布 server 一个包；web 包设为私有，不发布；不引入打包器；
发布内容用 `files` 白名单限定，不带源码与测试。

**镜像基础**：方案 B。基础镜像为 `node:24-slim`（Debian，glibc）。
- 用官方镜像自带的 `node` 用户（uid 1000）运行，不用 root。
- 数据目录固定为 `/data`，镜像内不放任何配置与凭据。
- 镜像设 `YUANSHU_HOST=0.0.0.0` 与 `YUANSHU_DATA_DIR=/data`（见 [ADR-0018](0018-startup-params-and-health-endpoint.md)）。
  挂载的宿主机目录若对 uid 1000 不可写，Server 按 ADR-0018 启动失败并报错，使用者需自行调整目录权限。
- [ADR-0013](0013-tech-stack.md) 的 Node 下限 22.19 不变；镜像运行的是 Node 24，两者不矛盾。

**镜像构建**：方案 A。多阶段；第一阶段构建并打出 npm 包，最终阶段在干净的 `node:24-slim` 里只安装该包。
镜像与 npm 包因此是同一份构建产出，镜像里跑通同时验证了 npm 包本身的结构。
具体怎么取包、依赖怎么装，留给 plan 用实验确定。

## 理由
- 命令名与子命令的写法被 Docker 入口和脚本引用后很难改；现在多一个 `serve`，比以后改裸命令的含义便宜。
- 单个 npm 包不会让发布出去的包依赖一个只存在于本仓库的包；不用打包器，少一个会出问题的环节。
- 选 Node 24 而不是 22，依据是更长的支持周期：22 的维护期约半年后结束，选 22 则镜像很快要再升级一次。不选 alpine，是为了避开 musl 对原生依赖的潜在问题。
- 多阶段加"镜像里只装 npm 包"，让两种发布物同源，也把"装出去能不能跑"变成每次构建都验证的事。

## 影响
- Node 24 的测试覆盖是遗留问题：CI 目前只跑 Node 22.19.0。是在 CI 里加 Node 24 矩阵，还是只靠镜像内的启动探测，易逆，留给 spec 定。
  ROADMAP 第 2 条的契约测试要在 Node 24 上也能跑，pi SDK 在 24 上的行为到那时才会被验证。
- spec 要明确：裸命令的行为与退出码；`files` 白名单的内容；基础镜像标签的锁定方式（标签或摘要）及其底层 Debian 版本（尚未核实）；
  镜像里的 `HEALTHCHECK` 探测手段（slim 镜像里不一定有 curl）。
- "把打好的包装到干净目录并启动一次，通过健康探测"需要在 CI 中验证，本仓库里能跑不代表装出去能跑。
- plan 要用实验确定：从构建阶段取包的方式，以及"装包"与"复制产物"哪个更能保证装出去能跑。
- 之后换基础镜像（例如升到更新的 Node）是单独变更；命令名与子命令的写法一旦发布不再改。
- 排除：两个命令入口；多个 npm 包；打包器；alpine；单阶段与复制宿主机产物的镜像构建。
