# ADR-0002: 薄环境：工具逻辑在 Server，环境只提供最小原语

状态：已定稿
日期：2026-10-16
可逆性：难逆
取代：无
被取代：——
引用入口：VISION「做什么」第 2 条、「不做什么」第 3、5 条；ARCHITECTURE「技术选型」环境一行

## 背景
agent 需要在多个环境里工作：Server 所在主机、远程主机、用户自建的容器。
以 skill 或 MCP 封装远程执行的做法，会把命令包进一层外壳：可读性差，
权限规则只能全放或全拒，既不优雅也不原生。
此前的 ssh 插件验证过另一种思路：在最低层注入"远程"，上层工具面保持同构，agent 无感。
约束：远程不应安装 pi SDK 或 Node，那过重。

## 候选方案
### 方案 A：远程驻留 agent 运行时
在远程装 pi 或 Node，agent 在远程跑，Server 只做转发。
能力完整不衰减。代价：每台都要装、要升级，状态散落在各机器上，Server 无法统一管理。
### 方案 B：薄环境
agent 循环与全部工具逻辑在 Server；环境只提供最小原语：读写字节、启动带标准输入输出的进程、
列目录、放文件。零安装档只依赖 POSIX 基础命令。
代价：常驻在环境内的运行时类能力不由原语直接提供（见影响）。
### 方案 C：以 MCP/skill 外挂远程执行
实现简单。代价：命令被外壳包裹，规则无法判断，体验不原生。

## 决定
方案 B。环境只有两种：Server 所在的基础环境，以及经 ssh 接入的环境。
Server 不创建、销毁、快照任何环境；需要隔离环境时，用户自建（容器里跑 sshd 亦可），
在 WebUI 里登记并连接。命令原样在环境中执行，不被包装。

环境按系统类型分为类 POSIX（Linux、macOS）与 Windows 两类，**Windows 环境是必须支持的**
（用户的办公文件与只有 Windows 版本的应用都在 Windows 上）。Windows 环境以 Git Bash 与
OpenSSH Server 为前置条件，Server 探测目标机是否具备，缺则提示安装；
命令经 Git Bash 执行，路径转译交给它。

## 理由
- 工具逻辑在 Server，读写、搜索、编辑在所有环境里同构，不随环境衰减。
- 命令原样执行，权限规则才能判断它，这是权限设计的前提。
- 远程零安装，换环境的成本接近零。
- 不管环境的创建，Docker 守护进程权限、容器生命周期这类问题整体消失。

## 影响
- 依赖环境内常驻运行时的能力不由环境原语直接提供：LSP 与调试器、skill 脚本的依赖，
  由环境自备。其中 LSP 与 DAP 走标准输入输出，将来可经"启动进程"原语在环境内拉起，作为上层能力评估。
- rg 与 fd 缺失时退回基础命令；是否由 Server 推送静态二进制补全，留给后续 intent。
- ssh 连接管理（持久连接、心跳、重连、多路复用）要升格为 Server 级服务。
- 跨环境文件传输是原语的一部分，不是外挂。
- 原语集合刻意最小，以便 ssh 之外的通道将来可接入，但本期只做 ssh。
- 路径解析按环境类型各自实现，"在不在 cwd 内"的判断依赖它（盘符、大小写不敏感、联接点）。
- Windows 上经 ssh 启动的进程可能不在用户的交互式桌面会话里，GUI 应用自动化可能受限；
  是否需要在用户会话里驻留常驻进程，取决于冒烟验证的结果。
- macOS 为 BSD 用户态，零安装档的命令需在 macOS 上单独验证。
- S0 需验证：在真实 Windows 机器上，ssh 原语（读写文件、执行命令、传文件）
  与 GUI 应用自动化的可行性。
- 一个静态二进制的常驻 daemon（加强档）留待有需要时再评估，本期不做；
  Windows GUI 自动化可能成为触发条件。
- 排除：Server 管理容器生命周期；在远程安装 agent 运行时。
