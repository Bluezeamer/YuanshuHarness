# ADR-0005: 客户端协议：事件流、排队与统一弹窗

状态：已定稿
日期：2026-10-16
可逆性：难逆
取代：无
被取代：——
引用入口：ARCHITECTURE「数据流」与「边界与约定」；VISION「做什么」第 1 条

## 背景
WebUI、命令行、IM 可能同时看同一个会话，随时断开再接上，任务不能因此中断。
pi SDK 的事件没有序号也没有回放，界面交互只有单槽位。
审批和 agent 的提问都需要弹窗，要决定发给谁、谁来答。

## 候选方案
### 方案 A：事件回放
Server 为每个会话维护事件缓冲区，客户端重连时按序号补发。
代价：要管理缓冲区的大小和淘汰，长会话占用高。
### 方案 B：序号加最近窗口的状态
事件带递增序号；重连时发最近若干条的状态与当前执行步骤，再接上实时事件。
代价：重连时要传一次窗口数据；窗口之外的历史需要客户端按需拉取。
### 方案 C：客户端直连 pi 事件，不加序号
最简单。代价：断线期间的内容丢失，无法发现缺口。

弹窗的候选：
### 指定审批设备
代价：该设备不在手边时任务卡住。
### 发给所有客户端，先答先赢
代价：需要在其余客户端上撤销已被回答的弹窗。

## 决定
方案 B 加"先答先赢"。
- 每个事件由 Server 打递增序号。序号仅是每个会话的单调计数器，用于快照与实时流的衔接
  和缺口检测，不保存事件，不用于回放。出现缺口就重新拉最近窗口。
- 重连只发最近若干条的状态加当前执行步骤，更早的历史按需往上翻；
  历史静态展示，不回放执行动画与中间路径。窗口只影响客户端显示，不影响 agent 的上下文。
- 会话运行中收到新消息，统一排队，在 agent 当前这一步结束后送达，所有客户端都能看到排队消息。
  停止操作从任何客户端都有效。
- 弹窗发给所有接入该会话的客户端，先答先赢，其余自动关闭。
  没有客户端在线时留在待处理队列，上线时补发，超时按拒绝处理。
- agent 向用户提问走同一套弹窗；超时后回给 agent"用户未回答"。
- 弹窗分两类：点选类所有客户端都能答；输入类（密码等）只允许在 WebUI 答，
  IM 收到时只提示"请到 WebUI 处理"。
- Server 在 pi 的单槽位界面之上做分发。

## 理由
- 单用户场景下，序号加窗口足够简单，不必维护回放缓冲区。
- 已完成的历史可由 JSONL 重建，只有"当前这一步"需要实时状态，序号用来衔接两者。
- 同时发消息基本是补充指令，排队比拒绝更顺手，也不打断当前步骤。
- 先答先赢让用户在手边任何设备上都能处理，不需要指定审批设备。
- IM 里输入的内容会留在聊天记录并经过第三方，密码不应经过它。

## 影响
- 协议里要有：事件序号、窗口拉取、排队消息、弹窗的类型（点选 / 输入）与撤销。
- 审批超时时长与等待上限待定。
- S0 需验证：单槽位界面在 Server 层分发是否可行。
- 排除：服务端事件回放；指定审批设备。
