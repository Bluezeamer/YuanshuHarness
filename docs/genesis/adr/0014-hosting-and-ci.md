# ADR-0014: 代码托管与 CI：GitHub 公开仓库，脚本化 CI

状态：已定稿
日期：2026-10-16
可逆性：易逆
取代：无
被取代：——
引用入口：ARCHITECTURE「边界与约定」；ROADMAP 第 1 条

## 背景
项目最终要开源。早先倾向 GitLab 内部开发、再同步 GitHub，
但同步两个平台、日后还要接两套 CI，成本高。
本机有高性能的 runner 资源（8 并发、14 核 20 线程），GitHub 的自托管 runner
在私有仓库上曾宣布按分钟收取平台费，随后推迟，截至 2026-10 未生效，也未撤回（来自第三方汇总，
未核对官方计费文档）。GitHub 官方安全文档建议自托管 runner 几乎不要用于公开仓库。
用户的 GitHub 账号是 Free 计划：按官方文档，分支保护与规则集在 Free 下只对公开仓库可用，
而 aisdlc 要求骨架合并后开启主干保护并做负向验证。

## 候选方案
### 方案 A：GitLab 内部开发，成熟后同步到 GitHub
本地 CI 性能好。代价：长期维护两个平台与两套 CI 配置，开源后协作者的 CI 接线仍要重做。
### 方案 B：只用 GitHub
一个平台，开源后无需迁移。代价：放弃现成的 GitLab 本地 CI 经验。

## 决定
方案 B，且仓库从一开始即公开（GitHub：Bluezeamer/YuanshuHarness）。
- 公开仓库在 Free 账号上可用主干保护，托管 runner 也免费。
- CI 逻辑写进仓库里的脚本（如 `scripts/check.sh`：类型检查、lint、单测），
  工作流只负责调用脚本。本地与 CI 跑同一份，将来换平台只改外层。
- CI 使用 GitHub 托管的 runner，不使用自托管 runner
  （公开仓库上任何人都能通过 PR 触发其上的代码执行）。
- CI/CD 的构建思路参考同类成熟项目的经验（如 pi、Codex、opencode 的做法），
  不自行发明流程。

## 理由
- 一个平台比双平台同步省事，开源后不用再迁移。
- 脚本化让本地也能快速验证，不依赖 runner。
- 托管 runner 对 Node 的类型检查与单测足够，也自带 Docker，后面连 ssh 容器做集成测试可行。
- 成熟项目的流水线已被大量使用验证过，借鉴比重新设计稳妥。
- 只有公开仓库才能在 Free 账号上开启主干保护，满足 aisdlc 的骨架关闭条件。

## 影响
- 骨架 intent 要带上 CI 脚本与工作流，并接入 aisdlc 的两个机械校验脚本；
  设计 CI/CD 时先看同类项目的做法。
- 需要在合并后开启主干保护与"流水线必须成功"，做法见 aisdlc 的接线说明。
- 仓库公开：提交历史、文档与技能都是公开的，提交前须自查不含凭据与个人信息。
- 排除：GitLab 同步；自托管 runner；私有开发阶段。
