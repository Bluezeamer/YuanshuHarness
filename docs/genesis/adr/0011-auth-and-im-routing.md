# ADR-0011: 客户端接入认证与 IM 路由

状态：已定稿
日期：2026-10-16
可逆性：难逆
取代：无
被取代：——
引用入口：VISION「不做什么」第 2、7 条；ARCHITECTURE「边界与约定」

## 背景
Server 持有所有环境的凭据，能在所有环境里执行命令。谁能连上 Server，谁就拿到了全部钥匙。
预期部署在受信的内网环境（如 Tailscale 组网），不面向公网。只服务一个人，
但 IM 接入天然带来"多个平台用户给同一个 Server 发消息"的情形。

## 候选方案
### 方案 A：不认证，依赖网络隔离
最简单。代价：内网里任何一台机器都能操作 Server。
### 方案 B：受限网段加令牌，IM 白名单路由
网络层缩小范围，应用层再认证，IM 另有来源校验。
### 方案 C：完整账号体系
多用户、OAuth、角色。代价：与"单用户"相悖，复杂度远超需求。

## 决定
方案 B。
- Server 默认只接受受限网段的请求（如 Tailscale 组网内的网段）。
- 所有客户端用访问令牌（或账号口令，实现时定）接入；失败多次后限制访问，作为底线。
- IM 接入由 Server 端控制响应哪些平台用户，名单外的消息直接丢弃。
- 不同的 IM 用户可以路由到不同的 agent，这是一张"平台用户 → agent"的路由表，
  不是多用户系统。
- 不做多用户、OAuth、账号体系。

## 理由
- 预期不在公网使用，网络层限制加令牌足以作为底线。
- 平台用户本身带有身份，Server 只需决定响应谁，不需要自建账号。
- 路由表让不同的 agent 响应不同的 IM 用户，在不引入多用户的前提下满足这类用法。

## 影响
- 启动参数里需要有"允许的来源网段"（见 ADR-0012）。
- Server 持有全部环境凭据，接入层一旦被突破，等于交出所有环境；本期接受这一风险，
  前提是部署在受信网络内。
- IM 的具体接入方式（Hermes 的做法未读过，做 IM 接入时再核对）、
  由 IM 用户发起的会话触发审批时谁来答，待定，倾向仍由本人在 WebUI 回答。
- 排除：公网暴露；多用户与账号体系。
