# 评审协议

适用于所有需要"评审"的地方：决策档与标准档的实现评审、静默类变更的多轮加固、快车道汇总报告的复核。

## 核心规则：评审者是新开的、空上下文的 subagent

- **为什么**：实现者的会话里装着自己的推理、取舍，和"这里我已经验证过了"的印象。在同一上下文里评审，会顺着实现者的思路去确认，而不是去怀疑它；换个角色再看一遍也一样。
  空上下文的评审者看不到这些，只能回答"这段代码是否满足这条需求"，评审的路径因此是清晰的、可追溯的。
- **每一轮都新开一个**，不复用上一轮的评审者——它对自己上一轮的结论已经有了立场。需要延续的信息（上轮发现了什么、修了什么）通过 `review.md` 传递，不通过会话。
- **怎么新开取决于所用的 harness**（原生 subagent、插件、另起一个会话都可以），本技能不规定；只规定一点：评审者的上下文是空的，只通过工件了解变更。
- **新开不了就如实说。** 当前环境确实无法新开评审者时，在 `review.md`（或报告的复核层）写"未做独立评审：<原因>"，并在交给人的回复里点明，请人另起一个会话按上面的流程评审。
  不要用同一会话里的"自评"顶替——那会让人误以为已经独立审过。

## 流程

1. **准备输入**（实现者做）：用 [assets/reviewer-prompt.md](../assets/reviewer-prompt.md) 填空。提示词里只放工件的路径和标识，不放实现者的转述（见下表）。
2. **新开 subagent**，把填好的提示词交给它。
3. **评审者工作**：只读代码，可运行测试和检查命令；把本轮记录追加到 `review.md`；回复一段简短摘要。
4. **实现者处理**：逐条修复、驳回（写理由）或推迟（附链接），结果写在 `review.md` 的"处理"列。驳回必须留下理由，因为人在 MR 上会读到。
5. **有修复就再来一轮**：新开下一个 subagent，范围是修复的增量，并要求它核对上轮的阻塞 / 重要项是否真的消失。
6. **收敛**：连续三轮仍有阻塞级问题 → 暂停，不要继续打补丁。这通常说明设计里有悬而未决的口径，回到 spec 澄清，必要时请人裁决或升档。

## 传给评审者的，和不传的

| 传（路径或标识，让它自己去读）| 不传 |
|---|---|
| `spec.md`、`intent.md` | 实现过程的对话、实现者的思路 |
| 评审范围：commit 区间或分支对比 | "这里我已经确认过没问题"一类的结论 |
| `review.md`（上轮记录）| 对问题严重程度的预判 |
| 测试与检查命令 | |
| 关注清单（静默类变更，已内置在提示词模板里）| |

## 评审者的权限

- 只读源码、测试、spec；可以运行测试与检查命令。不修改源码。
- 唯一的写入：向 `review.md` 追加本轮记录。让评审者自己写，不由实现者转录——转录时措辞会被不自觉地淡化。
- 拿不准的发现标"待确认"，写明还缺什么证据；不要当成确定的缺陷，也不要因为拿不准而省略。

## 人的位置

subagent 评审不替代 MR 上的人工评审。它给人看的是一份独立的、可追溯的发现清单，而不是作者的自述；
实现者驳回的发现，理由也都在 `review.md` 里，人在 MR 上可以直接核对。
