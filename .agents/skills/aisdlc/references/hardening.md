# 静默类变更的加固

适用：标准档或决策档命中了"静默"信号（用户数据的写 / 删 / 迁移、并发与乱序、对外部系统真实行为的假设、约定一致性、熔断与兜底）。

静默的错在前置阶段看不出来——它们藏在实现细节里（一个恒真的条件、一处不一致的约定）。所以防线放在实现之后：
让测试证明、让没参与实现的评审者挑刺、让真实运行时验证。每条做法背后的真实案例见 [routing.md 的"加固清单的出处"](routing.md)。

## 做法

1. **把不变量写进 Requirements。** 用"必须 / 不得"句式，例如"持续断连超过宽限期必须提示"。不变量既是评审的靶子，也是测试的断言；实现步骤会变，不变量不会。

2. **失败先行。** 每条新测试必须在**旧实现**上失败（或去掉修复后失败）；Proof 表里记录"旧实现下失败：是"。
   能在旧实现上失败，才说明测试真的在测这件事。
   全新的功能在旧实现上必然失败（入口都不存在），这证明不了什么；对其中的**不变量**类需求要做变异验证：故意去掉对应的保护或引入对应的错误，该用例必须变红。变异结果记入 `review.md`。

3. **fixture 用真实形状，不手造。** 测试数据从真实函数的输出构造。手造的数据只验证了你的想象，主场景是否真的走通它说明不了。

4. **只在真实运行时才走到的分支，必须有真实运行时验证。** 对第三方库、运行时、平台的回调参数、事件时序、生命周期的假设，
   类型检查和单元测试拦不住，要在真实环境里跑一遍（E2E、冒烟脚本、真实服务）。

5. **评审交给新开的空上下文 subagent。** 协议见 [review.md](review.md)，提示词和关注清单在 [reviewer-prompt.md](../assets/reviewer-prompt.md)。
   评审者不是作者，也不继承作者的会话，所以才可能怀疑作者的假设。

6. **修复本身也要被评审。** 评审后的修复，新开下一个 subagent 评审增量，要求它核对上轮的问题是否真的消失，而不是只确认"看起来改了"。
   修复是新引入回归的高发处：越是在评审压力下补的守卫和早退，越容易挡住本来正常的路径。

7. **新增的校验和自检，用已知坏输入证明它会失败。** 不会失败的检查不是检查。

8. **收敛规则。** 连续三轮评审仍有阻塞级问题，**暂停**，不要继续打补丁。这通常意味着设计层面有悬而未决的口径（比如两条分支的判据不一致），
   继续修只会不断引入新回归。回到 spec 把口径定下来，必要时请人裁决或升档。

## 记录

每一轮评审写进 `review.md`（[assets/review.md](../assets/review.md)），包含级别、位置、发现、处理。不要追加进 spec——spec 只在 Requirements 变化时修改。
否则 spec 会涨成评审日志，几周后的读者分不清哪些是需求、哪些是修补。
