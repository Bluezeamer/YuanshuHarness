## 0. 机械校验

地基层，随骨架接入。要做到四件事：

1. 每个 MR 跑 `aisdlc_index.py --check`（`Status` 与目录一致、链接有效），并把生成的索引作为产物保存。
2. 分支名属于快车道（例如 `lane/<名>`）的 MR，用**目标分支上的章程**跑 `aisdlc_check_lane.py --base <目标分支> --report`。需要完整历史：浅克隆会断掉 merge-base，三点 diff 会报 no merge base。
3. 章程路径和 CI 所跑脚本的路径（`scripts/aisdlc/`，直接引用技能时是 `.agents/skills/aisdlc/scripts/`）的改动必须经负责人批准。后者的理由：CI 跑的是 MR 分支上的脚本，快车道 MR 若能改脚本，就能让检查放过自己。
   平台支持"按路径要求指定人批准"就用它；不支持或版别不够，就用"只有维护者能合并，合并前人审 MR"兜住，并如实告诉用户这一档强度较弱。
4. 主干要求流水线通过才能合并。

CI 要跑的两个脚本（`aisdlc_index.py`、`aisdlc_check_lane.py`）需随项目仓库提供（复制到 `scripts/aisdlc/`），CI 才调得到。脚本契约见 [automation.md](automation.md)。缺少前提要让作业失败，不要跳过。

## 1. MR 评审

- **触发**：MR 事件的流水线（新建、推送更新）。
- **输入**：目标分支到源分支的 diff（需完整历史）；本 MR 新增或修改的 `intent.md` / `spec.md`，让评审者对照需求而不是凭印象；提示词用 [reviewer-prompt.md](../assets/reviewer-prompt.md) 的 A 节，只给路径。
- **执行**：`<harness-run>`，工具限定只读，设超时。
- **输出**：脚本把文本发成 MR 评论（bot 身份），评论带固定前缀便于识别。评审不批准也不阻断，批准权在人。
- **权限**：读 MR、发评论。不需要 push，不需要创建 MR。
- **失败**：发评论失败要让作业失败。评审作业设为允许失败（平台上显示为警告而不是红）【建议】，免得模型服务故障挡住合并，同时故障仍然可见。
- **验收**：开一个 MR，作业跑完，MR 上出现 bot 身份的评审评论。

## 2. 评论命令

在 MR 评论里以 `@<bot名> <形态>` 开头。形态：

- `ask <问题>`：回答，回复在同一线程；只读。
- `review`：重新评审，同上节。
- `fix <描述>`：见下，两阶段。

### 触发链路

事件需要带着评论内容去起流水线。平台若原生支持"评论事件触发流水线并带评论正文"（GitHub 的评论事件应当如此，⚠️未验证），直接用。
GitLab 没有，需要 **Webhook + 薄中继 + 触发 API**。中继自己不持有执行环境（没有 harness、不 clone 仓库），纯转发；语言不限，体量约百行。

中继契约：

1. 验签（HMAC）。失败返回 **4xx**【建议】：原经验返回 200，平台的投递日志显示"成功"而事件被静默丢弃，是最危险的假绿。
2. 只处理 MR 评论；忽略 bot 自己的评论，防止自触发。
3. 解析 `@bot <形态>`；未知形态回复用法提示。
4. 按评论 id 去重【建议】：原经验无幂等，平台的"重新发送"会重复触发。
5. 用只能起流水线的触发令牌起流水线，传变量：形态、内容、MR iid、评论 id、讨论串 id。
6. 无鉴权，只靠验签，不要暴露公网；必须常驻运行（做成服务），否则关掉终端后命令静默失效；必填环境变量缺一个就启动失败。

流水线只在收到形态变量时才创建对应作业，其他来源的触发不创建流水线，免得产生噪音。作业调用 `<harness-run>`，由脚本把回复 POST 回**同一讨论串**。

**状态**：讨论串内 bot 的标记评论就是状态。线程里已有终态标记（如 `[fix 完成]`、`[fix 已取消]`）就不再重复触发；bot 自己的评论不触发。

### fix（默认接入）

两阶段，人闸门在中间：

1. `@bot fix <描述>` → bot 回复 `[fix 待确认]`：说明将修改哪个分支、做什么。
2. **MR 作者**回复单独一句「确认」才执行；「取消」放弃。执行后回复 `[fix 完成]` 或 `[fix 已取消]`。

要点：

- **确认者必须是 MR 作者**，不是任意评论者，防止任意评论者触发改码与推送。载荷缺少作者信息时 fail-closed：不触发，返回诊断。提示文案也要写"MR 作者"（原经验的文案写成"非 bot 用户"，与实现不一致）。
- 执行：harness 在 runner 容器里改代码、提交，**只推 MR 的源分支**。MR 随之更新，机械校验与 MR 评审重新跑。
- **默认开是安全的，因为闸门是 MR 加受保护主干。** bot 无权推主干，无合并与批准权；源分支上的改动要经 MR 流水线和人审才能合并。前提是仓库只接受可信贡献者的 MR；接受外部 MR 的项目关掉 fix（理由见 [wiring-gitlab.md](wiring-gitlab.md) 的令牌暴露面）。
- 权限：bot 需要 push 权（开发者级）；**不给**合并、批准、更新项目设置、删除。主干保护须真正生效，含关闭 force push；bot 不得持有能绕过保护的凭据。
- 范围：fix 只改本 MR 已有变更的范围。若要碰数据形状、ADR，或越出快车道章程，停下并升档（章程越线会被机械校验拦下）。
- 提交身份：commit 作者与推送身份都应是 bot，换令牌时一起换。把 bot 名放在一处配置，不要散落硬编码（原经验散落在至少两处，换执行者要同步改）。
- 推送之后核对远端真的变了：失败输出的末行与成功很像。

**验收**：`@bot ask …` 在线程内得到回复；`@bot fix …` 得到 `[fix 待确认]`，作者「确认」后源分支出现 bot 的提交；非作者的「确认」不触发。

## 3. 监控回边

把"线上出事了"这个事实转成一份新的 intent，让循环成环。

- **触发**：定时流水线。
- **检测：确定性脚本，不涉及模型。** 探测健康端点；判 up 的条件要具体（例如状态码 200 且响应体含约定字段），其余（连接失败、超时、非 200）一律判 down。执行体用运行时自带的 HTTP 能力写，作业镜像里不一定有 curl。
- **分级响应**（示例）：连续失败 1 次只记录；连续 ≥2 次建发现 issue；24 小时冷却，每日至多一个（当日已存在则复用）；恢复则复位。阈值写在版本管理的配置里。
- **状态**：专用 issue（如 `[monitor] state`）的最新 note。首跑自动创建；读取时向前扫最新一条**可解析**的 note，所以人在上面的评论不会破坏状态；只在状态变化时写（稳态零噪音）。该 issue 被删则重建、计数归零，最坏延迟一个周期，别删。
- **输出**：发现 issue，作者是 bot，正文是渲染后的 [assets/intent.md](../assets/intent.md)（`来源` 填"监控告警"并附脱敏后的证据，规则见 AGENTS.md 的敏感信息一节）。模板渲染用字符串替换，别用 sed，特殊字符会损坏替换。
- **人闸门**：人分诊，选"修 / 排期 / 驳回"，驳回用来调阈值降噪。接受后才写成仓库里的 `docs/intent/active/...`，再按判档走。发现 issue 只是分诊队列，不是 intent；"仓库是事实源"在这里有意让位于"零额外权限"。
- **权限**：读 issue、发 note、建 issue，不需要写仓库。
- **演练**：用显式变量覆盖探测地址，手动触发流水线，把失败路径完整走一遍而不碰生产。定时与手动来源的流水线**不得**触发部署类作业。
- **已接受的风险**：监控依赖平台可用性，平台挂了监控也挂。

**验收**：手动触发一次，作业绿，状态 issue 最新 note 为 up；演练一次，生成真实的发现 issue，验证后关闭。
