# 判档详解与校准

本文件分两部分：前半是与具体项目无关的边界案例和升降档规则；后半是一个真实项目的回溯，**只作经验参考**，其中的具体情形不构成规则。

## 边界案例

| 情形 | 档位 | 理由 |
|---|---|---|
| 调整点击热区、动效时长 | 快车道 | 响亮、可逆、局部 |
| 修"按钮点了没反应"，原因在组件内的事件绑定 | 快车道 | 无状态；行为 bug 先写失败的测试再修 |
| 修"新增的记录归属错了"，原因在事件到数据的归属解析 | 标准档 + 加固 | 写用户数据、依赖多处约定、错了不报错 |
| 加"级联删除" | 标准档 + 加固 | 删用户数据；错了是静默丢失 |
| 全面视觉改版 | 标准档 | 响亮可逆，但体量远超快车道上限 |
| 改默认交互行为（例如搜索默认走哪条路径）| 标准档；章程已覆盖该目录则快车道 | 行为变化，但响亮可逆 |
| 给数据模型加字段 | 决策档 | 持久化形状变化，难逆 |
| 新增一个写入本地存储的设置项 | 标准档；涉及迁移则决策档 | revert 之后，使用者那里已写入的值不会被清掉 |
| 用户一次说了两件不同档位的事 | 拆成两个 intent | 一个 intent 一个档位 |

**拿不准的两个反问**：

- "如果这个改动上线后出错，**谁会先发现，多久**？" 使用者当场发现 → 偏轻；要靠数据对账、告警或几天后的投诉才发现 → 偏重。
- "revert 之后，使用者那里已经产生的状态还能干净吗？" 不能 → 偏重。

## 降档与升档

- **降档**（标准 → 快车道）：只在改动**完全落在已批准章程的路径与体量内**时。章程由人批准一次，之后判定交给 CI，不靠每次口头争论。
- **升档**：任何时点发现原判档位低估了风险就升。升档不是失败，是流程在起作用。触发条件：越线、要改 ADR、新增持久化契约、评审连续三轮阻塞级、实现时发现范围比 intent 描述的大一倍。
- 升档后补齐该档应有的产物，已做的工作保留，不推倒重来。

## 实践回溯：一个真实项目的 34 个变更

数据来自一个新项目（书签同步工具）在创世后头几周产出的 34 个 intent（及对应 spec/plan）。以下是用标题与统计粗分的结果，**未逐份细读**，用来校准判档轴，不是结论。

| 回溯档位 | 数量（共 34 个 intent）| 代表 |
|---|---|---|
| 决策档（真正需要拍板难逆决策）| 1 | 项目骨架 |
| 标准档 + 加固（静默）| 9 | 同步核心、扩展回写、强制同步、事件路径归属、文件夹级联删除、部署产物、状态抖动 |
| 标准档（新能力，响亮）| 14 | 分类器、历史视图、统一搜索、侧栏树、智能拖拽、移动端 PWA、全站视觉重做 |
| 快车道候选（响亮可逆小改）| 9 | nav-hit-target、nav-polish、nav-smoothness、interaction-performance、drop-landing-layout、bookmark-interaction、sidebar-usability、crossfolder-drag、search-default-engine |

另有一个**中途升档**的真实案例：分类器接入（标准档）实现时暴露出书签节点必须是 `Y.Map`，
由此新增 ADR-009（难逆的数据形状决策）。这正是"实现中发现要改数据形状 → 停下来升到决策档"该发生的样子。

支撑这套判档轴的观察：

- **返工集中在静默类。** 带 `Review 修复` 节的 5 份 spec 共 18 个评审轮次记录，全部是同步 / 回写 / 事件队列 / 连接状态与 Service Worker 生命周期 / 部署产物这类"出错也不报错"的问题（例如服务器宕机时 popup 仍显示绿点"已连接"）；快车道候选一轮都没有。
- **这些缺陷是实现层的**：死代码、键约定不一致、重放载荷丢字段、并发重叠、守卫改动引入新回归。前置 spec 看不出来，是事后评审和 E2E 抓到的。
- **一次 intent 捆三件事的代价**：把"强制同步（静默）+ 侧栏滚动保留（响亮）+ 可配置后端"捆成一个 intent，整份 spec 涨到 156 行，其中 7 轮评审记录。
- **genesis 几乎没被回头改**：9 份 ADR 无一被取代，仅新增 1 份。宏观层是慢变量，循环不必每次都惦记它。
- **自发的简化已经出现**：后期 5 个 intent 没写 plan；三个相关 intent 共用一份 plan；UI 类 plan 只有一张文件表加验收。

## 加固清单的出处

[hardening.md](hardening.md) 和 [reviewer-prompt.md](../assets/reviewer-prompt.md) 里的每条做法，都来自上面这个项目的具体教训：

| 做法 | 当时发生了什么 |
|---|---|
| 失败先行 | 状态抖动修复的三个新用例在旧行为下实测全挂（3/6 通过），才确认测试真的在测这件事 |
| fixture 用真实形状 | 剪枝修复的测试用手造的映射表，把"主场景其实没修好"掩盖了；另一次 fixture 与真实输出的形状不符，断言在真实数据下是空断言 |
| 真实运行时验证（E2E）| 浏览器书签事件的回调签名是 `(id, info)`，三个 handler 都取了第二个参数——移动和删除事件从来没生效过；类型检查和纯函数测试都拦不住，真浏览器的 E2E 一跑就现形 |
| 评审清单·死代码 | 剪枝里的文件夹分支条件恒真/恒假，`pruned.folders` 永远是 0 |
| 评审清单·约定一致性 | 顶层文件夹的键，一处归一化成 `root`、另一处仍是 `0`，未映射的顶层夹被误剪 |
| 评审清单·重入与并发 | 回写正在执行时用户点了"覆盖"，回写收尾把基线写回旧值，之后每次都命中熔断 |
| 评审清单·辅助结构 | 剪枝只清文件夹映射，书签映射残留，每次覆盖都累积一批 |
| 评审清单·重放载荷 | 重放待办队列时只带了 `{ id }`，创建事件造出空名幽灵夹，移动事件把书签挪回未分组 |
| 评审清单·守卫挡住首次路径 | 一次修复把守卫写成"nodeMap 非空才导入"，新装用户的首次导入永远不发生 |
| 评审清单·假成功 | 服务器宕机时 popup 仍显示"已连接"；另一次是成功条数被状态函数抹掉，用户永远看不到 |
| 评审清单·对外部行为的假设 | 构建改动让 Service Worker 变成 ES module，清单里没声明 `type: "module"`，注册失败，导入和同步全部静默失效 |
| 修复也要被评审 | 上面"守卫挡住首次路径"那一例，就是第 5 轮的修复引入、第 6 轮才抓到的阻塞级回归 |
| 收敛规则 | 同一份 spec 积累到 7 轮评审，后几轮修的多是前几轮补丁的副作用 |
