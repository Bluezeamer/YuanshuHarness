# 标准档流程

适用：既定边界内的新能力或行为变更，且不触及"难逆"信号。命中"静默"信号时在此基础上加固（见 [hardening.md](hardening.md)）。
这一档的目标是把前置把关压缩成**一次评审**，把精力留给实现后的验证。

## 步骤

1. **一次会话产出 intent + spec。** agent 在同一次会话里写两份文件，人一次读完、一次评审。拆成两个闸门没有意义：标准档的 intent 的"期望结果"与 spec 的 Requirements 高度重合。
   - **intent**（[assets/intent.md](../assets/intent.md)）：来源、问题（有根因就写根因证据）、期望结果、不做什么、需要人拍板的点。`Lane: build`，附一句 `Why:`。
   - **spec**（[assets/spec.md](../assets/spec.md)），写成 **delta**：只写"这次变更相对既有约定新增或改变了什么"。ARCHITECTURE 和 ADR 已经讲过的背景与整体设计只链接，不复述。
     - Requirements 用稳定编号 `R1.` `R2.`，每条可验证。测试用例引用这些编号，"系统现在是什么样"就由测试回答，不必另写一份状态文档。
     - Proof 表把每条 Requirement 对应到具体的测试或命令。
     - Design 只在引入新设计时才写。
2. **闸门：人一次评审 intent + spec，并确认档位。** 这是标准档唯一的前置闸门。
3. **plan 按需。** 满足任一条才写：跨多个包或目录；有 ≥3 个存在先后依赖的步骤；需要特定的迁移顺序。否则直接实现，步骤写在 MR 描述里。
   写 plan 时，实现中的偏离写进 `Deviations`，与对应代码同一次提交，不需要重新审批。
4. **实现。** 有行为断言的需求先写测试。命中静默信号则同步执行 [hardening.md](hardening.md)。
5. **评审。** 实现完成、开 MR 之前，按 [review.md](review.md) 新开空上下文的 subagent 评审，至少一轮；命中静默信号则多轮，直到没有阻塞级问题。评审记录写进 `review.md`，不写进 spec。
6. **MR。** 描述里附：Requirements → Proof 对照、测试结果、diffstat。由 code owner（人）最终评审。
7. **关闭。** 先确认 intent 里列的合并后动作（例如骨架的"开启主干保护"）已由用户做完并验证，没做完不关。然后 `Status: closed`，整夹移入 `docs/intent/done/`。
   关闭的是项目骨架时，向用户**提一次**：还可以接入 harness 介入循环的触点（MR 评审、评论命令、监控），入口见 [wiring.md](wiring.md)。是否接入由用户定，之后不再催。

## 写 intent 与 spec 时的几条经验

- 用户一次提了几条诉求，先按档位拆，再决定拆成几个 intent。同档位、同一个目标的诉求可以合并；不同档位的不要合并。
- 来源是用户反馈时，把用户的原话或现象和你查到的**根因**分开写。现象是用户的，根因是证据；评审的人需要能分别核对。
- 标准档的 spec 通常 25–60 行就够了。如果写到 150 行，先检查是不是把评审日志追加进了 spec（应写进 `review.md`），或是把几件事捆在了一起。
