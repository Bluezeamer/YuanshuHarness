# 接线：让 harness 介入循环

要为项目接入 CI、调整平台设置，或让 harness 在评审、命令、监控这些触点上自动介入时读本文件。
分三处：本文是总图与原则；[wiring-touchpoints.md](wiring-touchpoints.md) 讲每个触点的契约；[wiring-gitlab.md](wiring-gitlab.md) 是 GitLab 上的落地（其他平台暂无经验，见末节）。

## 接线是什么

循环里的触发点原本靠人推动：开 MR、问一句话、盯着线上。接线是把 harness 接到这些触发点上：事件到来，平台起一个**无头**的 harness 进程干活，产出写回平台（评论、issue、提交），人保留闸门。
CI 里的机械校验（索引、快车道越线）只是地基，不是全部。

## 前提：harness 要提供什么

- **无头运行**（必需）：非交互、一次性。给定提示词与工作目录，输出最终文本，用退出码表示成败；能限定可用工具（只读或可写）、指定模型、设超时；凭证从环境变量读。
  下文把这条命令记作 `<harness-run>`，写法由项目所用的 harness 决定，本技能不规定。
- **派生 subagent**：本地独立评审用（见 [review.md](review.md)）。CI 里的作业本身就是新进程，不需要。
- **工具调用前的拦截点**（可选）：用来做进程级围栏，见下。
- 没有无头模式，就只能接机械校验，其余触点不做，如实告诉用户。

## 触点与顺序

| 触点 | 触发 | 产出 | 人的位置 | 经验 |
|---|---|---|---|---|
| 机械校验 | 每个 MR | 流水线红或绿 | 合并 | 脚本有单测；YAML 未在真实 runner 上跑过 |
| MR 评审 | MR 事件 | 一条 MR 评论 | 合并 | 已实践 |
| 评论命令（ask / review / fix） | MR 评论里 @bot | 线程内回复；fix 会推送到源分支 | fix 先由 MR 作者确认；合并永远是人 | 已实践 |
| 监控回边 | 定时 | 发现 issue，正文是 intent 模板 | 分诊后才成为 intent | 最小形态已实践 |

IM 入口、让模型做分级的只读诊断：没有经验，不展开。

顺序：

1. 机械校验随**骨架**一起接（project-genesis 阶段 4）。骨架 MR 自己带来 CI，合并时基线分支上还没有保护。
2. 骨架合并后，用户在平台上开启**主干保护与"流水线必须成功"**。这是平台设置，不在仓库里，所以不属于骨架；它必须早于下面所有会给 bot 写权限的触点。
3. 再接 MR 评审。一条评论走通"镜像 → harness → 模型 → 平台 API → 评论"整条信任链，后面的触点都建在这条链上。
4. 再接评论命令，先 ask / review，后 fix。fix 要 bot 有推送权限，所以依赖第 2 步。
5. 最后接监控回边，它需要一个已部署、可探测的对象，通常要等项目有了可部署的版本。

第 3 到 5 步各是一个独立的 intent，不要捆在一起。按本技能自己的判档，它们引入新的运行时或部署形态、触及权限边界，属**决策档**，先有 ADR 再动手。

## CD 在哪里

CD 不是 harness 触点，但会影响顺序：监控需要已部署的对象，部署凭据也和令牌暴露面相关。本技能**没有 CD 的实践经验**，这里只定位置，不展开做法。

CD 的形态与时机在创世时由"交付形态"ADR 定下，读它，并看 ROADMAP 里的交付条目：

| 交付形态 | 接入时机 | 典型触发 |
|---|---|---|
| 部署类服务 | 骨架合并、主干保护开启之后尽快，先部署一个空壳服务（健康端点可探测、响应带版本），尽早暴露环境问题 | 合并主干，或手动 |
| 应用、库 | 用户认为有第一个可用版本之后；CI 里"能打出包"从骨架起就该有，"发布"才是 CD | 打 tag |
| 静态站点 | 同部署类，目标是托管 | 合并主干 |
| 不交付 | 无 CD，监控触点一并跳过 | 无 |

要点：

- 首次接 CD 属**决策档**：新的运行形态，持有发布或部署凭据。交付形态 ADR 已定的，按 ADR 做；没定的，先补 ADR。
- 应用与库的"首次发布"是条件式条目：每次关闭变更时看是否触及条件，问用户一次，不要当普通排队项。
- 部署作业只在主干（或受保护的 tag）上跑，凭据放受保护变量，不得被 MR 流水线读到。fix 会推送到源分支，所以这条必须严格。
- 部署之后校验响应里的版本确为新版本；只验"能 curl 通"，旧版本仍在响应时是假绿。
- 与触点的关系：MR 评审、评论命令不依赖 CD，可与之并行；监控依赖部署类 CD。

## 通用原则

1. **触发面与执行面分离。** 触发面（Webhook、定时、MR 事件）只负责把事件变成"起一个作业并传变量"；执行统一跑在 runner 的隔离、无状态容器里。触发面因此可以很薄，执行环境只有一份。
2. **模型只产出文本，确定性动作由脚本执行。** harness 给出评审意见、回答、修改；发评论、推送、建 issue 由脚本调 API 完成。"模型说了什么"和"系统做了什么"成为两件可以分别检查、分别限权的事。
3. **状态存在平台上，不另起存储。** 讨论串里 bot 的标记评论、专用 issue 的 note，就是状态机。作业无状态、可重放，所以每个动作要**幂等**：重复触发不重复评论、不重复建单。
4. **身份分离，可审计。** 自动化用独立的 bot 账号；人不冒充 bot，bot 不冒充人，看作者就知道是不是自动化。合并和批准永远是人。
5. **最小权限，先问"真需要写吗"。** 监控回边最初的设计需要 push 权限，被质疑后改成"只建 issue"，权限零变更。给权限之前，先找不需要它的做法。
6. **检测用确定性，判断才用模型。** 监控的探测是不涉及模型的脚本；越过阈值之后才调用模型，由触发层级决定它能做什么。
7. **围栏分层，外加人闸门。** 见下节。
8. **防假绿。** 自动化的"成功"要验证确实成功：缺少前提（工具、变量）必须**失败**，不能跳过；失败的投递不能返回成功码；推送之后要核对远端真的变了。

## 围栏分层

```
VM 隔离（物理边界）
 └ 服务端：分支保护 + 最小角色
    └ 进程级：harness 的拦截点或扩展（软约束）
       └ 人闸门：fix 先确认，合并永远是人
```

- 进程级围栏只是**软约束**。按命令正则拦"推送到主干"，挡不住 `git -C <目录> push`、带环境变量前缀的写法、`--all` / `--mirror`、在主干上裸跑 `git push`；
  冻结路径若只拦"写入 / 编辑"工具，经 shell 写文件就绕过；冻结清单文件不存在时整道防线空转。它的价值是抬高误操作的成本、让意图显式。
- 真正的兜底是服务端权限、VM 与人闸门。**agent 不应持有能绕过分支保护的凭据。** 在 GitLab 上，Owner 的普通 push 不受保护分支约束（见 [wiring-gitlab.md](wiring-gitlab.md)）；agent 拿着 Owner 的钥匙，分支保护就等于没有。
- 围栏要做**负向验证**：真去试一次被禁止的动作，看它被拦住。

## 分工

| 用户做 | agent 做 |
|---|---|
| 在平台上建 bot 账号、令牌、触发令牌、Webhook；改保护分支与合并检查；注册 runner；把令牌存进平台变量或服务环境 | 写 CI 配置、作业脚本、中继；把 CI 要跑的两个脚本放进仓库的 `scripts/aisdlc/`；本地能验的先验；写好验收清单并带用户逐步核对 |

- 令牌由用户创建，直接存进平台变量，**不要让用户把令牌贴进对话**；agent 的配置里只引用变量名。
- agent 动不了的平台设置，不要假装做了：写清"请去哪里点、期望看到什么"，等用户回报。

## 动手前先问用户

- 目标平台（GitLab / GitHub / 其他），自托管还是 SaaS，版本与版别。有些能力随版别而异，例如"要求代码负责人批准"。
- runner / 执行环境是什么，是否容器隔离。
- harness 的无头命令怎么写，模型服务从 runner 是否可达。
- 谁有管理员权限（建 bot 账号、改出站请求白名单、改保护规则都要）。
- 默认分支叫什么；是否接受外部贡献者的 MR。后者决定令牌的暴露面，也决定要不要开 fix。

## 逐阶段推进与验收

每个阶段结束都有"期望结果"，没看到就不进入下一阶段。这套接线最常见的失败是**某一步静默失败，后面全部无声**。
每阶段请用户贴出实际看到的页面或命令输出，agent 核对后再继续。

全部接好后做一次完整回路：开一个 MR，看到评审评论；在评论里 @bot，线程里有回复；跑一次监控演练，生成发现 issue。
再各做一条负向验证：用 bot 令牌直推主干应被拒；越出章程范围的快车道 MR 应被拦；非 MR 作者回复"确认"不应触发 fix。

## 与本地评审的关系：叠加

CI 评审和 [review.md](review.md) 的本地评审是两层，互不替代：

- 本地评审：实现者在开 MR 之前派生 subagent，记录写进 `review.md`。
- CI 评审：MR 上由新进程执行，天然是空上下文。用 [reviewer-prompt.md](../assets/reviewer-prompt.md)，只给路径；结论发成 MR 评论，不写 `review.md`。
- 人在 MR 上两份都看。本地确实新开不了 subagent 时，CI 评审是兜底，但交给人的回复里仍要照实写"本地未做独立评审"。

## 没有经验的平台

本技能目前只有 GitLab 的落地经验。目标是别的平台时，按本文的原则和 wiring-touchpoints 里的契约，用搜索或已有知识实现，并在交付里标明哪些没经过验证。
做完后问用户愿不愿意把踩到的坑沉淀成 `wiring-<平台>.md`，供下一次使用。
