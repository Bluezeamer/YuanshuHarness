# 快车道流程

适用：改动完全落在某条已批准的章程范围内——响亮、可逆、局部。
这类改动的错误使用者一眼就能看到，revert 一个 commit 就能收拾，前置审批只会增加等待。
所以快车道用**护栏**替代事前审批，用**汇总报告**替代逐项文档；审计粒度由 commit 保留。

## 建立章程（一次性，人批准）

用 [assets/charter.md](../assets/charter.md)，放在 `docs/lanes/<lane>/charter.md`。章程要写死、可被机器校验，不能靠自觉。
"准入"一节里的 `toml` 代码块由 CI 脚本读取（格式与脚本见 [automation.md](automation.md)），各项的取舍如下：

- **allow（路径白名单）**：本通道允许改哪些路径。只圈**纯展示**代码；会写入、删除数据的模块，即使放在展示层目录里也要排除（或先把数据写入层拆出去）。
  否则"小改动"可以悄悄变成静默类变更而不被拦下。
- **deny（路径黑名单）**：至少包含宏观文档目录，以及所有承载契约的文件（数据 schema、类型定义、通信协议、消息格式）。
  "不改数据模型和接口"没法直接判断，只能用"契约文件都在黑名单里"来近似——所以仓库结构要能把契约文件隔离出来。
- **max_files / max_lines**：单个 MR 的体量上限（本通道自己的 `reports/` 目录不计入）。
- **checks**：必过检查，例如 lint 和既有的回归套件。
- **升级规则**：越过任一条 → 停下，转标准档，写正规 intent。
- **归属**：一条通道一个负责人，或按目录划分。多人同改同一批文件会冲突，而且分不清谁对报告负责。
- **合并节奏**：每天 rebase 主线（长期分支会漂移）；满 N 个 commit 或满一周就开 MR，不攒成大 MR。

章程由人批准后合入主干。CI 对照**主干上的章程**判定 MR，而不是 MR 自己带的版本——否则 MR 可以先把白名单改宽，再放行自己。

## 日常工作

1. 在通道分支 `lane/<lane>` 上改。每个小改动一个独立 commit，Conventional Commits 格式，让单个 commit 就能读懂意图；
   commit 脚注写 `Source: <谁提的 / 哪次反馈>`——快车道没有 intent，这是"需求从哪来"唯一的追溯点。
2. 修行为 bug：先写失败的测试，再修。纯视觉改动不强制新增测试，但必须跑通章程规定的检查。
3. 越线就停。CI 对照章程检查 MR 的改动范围，越线直接拦下（脚本见 [automation.md](automation.md)）。

## 汇总报告

MR 合并时附一份报告（[assets/report.md](../assets/report.md)），存到 `docs/lanes/<lane>/reports/<YYMMDD>.md`。它是事后补出的一份压缩版 intent + plan。三层：

- **机械层**：由命令或脚本产生，不经过模型，所以可信——commit 列表、diffstat、章程越线检查的结果、必过检查的结果、视觉改动的前后截图。
- **叙述层**：agent 按主题归纳"改了什么、为什么"。
- **复核层**：新开一个空上下文的 subagent，对照实际 diff 核对叙述层与机械层是否一致，写一行结论。协议见 [review.md](review.md)，提示词用 [reviewer-prompt.md](../assets/reviewer-prompt.md) 的 B 节。
  写代码的 agent 自己写的叙述不能当证据。

人审机械层和截图；有疑点再下钻 diff。审的是报告，不必读完整 diff，这正是快车道省下来的时间。
